## 1. 문제 정의

### 1.1 현재 상황 (As-Is)

매일 수업 전, 원장님은 "오늘의 시험지 공장"의 유일한 직원입니다.
반마다, 학생마다 진도가 다르니 문제집을 뒤져 진도에 맞는 문제를 찾고,
쉬운 문제만 몰리지 않게 난이도를 눈대중으로 맞추고, 오려 붙이듯 시험지를 만듭니다.
이 공정이 **매일 30분~1시간**씩 반복되고, 바쁜 날에는 품질이 흔들립니다.

핵심 고충 4가지:
1. **문제 고르는 시간이 너무 오래 걸림** — 진도에 맞는 문제를 일일이 찾는 작업 자체가 부담
2. **난이도/유형 균형 맞추기 어려움** — 수작업으로는 쉬움/보통/어려움 비율 조절이 힘듦
3. **매일 반복되는 루틴** — 하루도 빠짐없이 만들어야 하니 누적 피로가 큼
4. **학생별 진도 관리 복잡** — 학생마다 진도가 달라 각자 다른 시험지가 필요

### 1.2 목표 상황 (To-Be)

수업이 끝나면 "오늘 어디까지 나갔는지"만 입력합니다.
다음 수업 전에 접속하면 **그 진도에 맞는 일일테스트가 이미 완성되어** 기다리고 있습니다.
훑어보고, 마음에 안 드는 문제는 1클릭으로 교체하고, 인쇄 버튼을 누르면 끝.
시험지 공장은 자동화되고, 원장님은 가르치는 일에 시간을 씁니다.

### 1.3 왜 지금인가? (Why Now)

- 원장님 **본인이 매일 직접 겪는 문제** — 절박함과 검증 환경이 동시에 갖춰짐
- AI가 수학 문제를 생성·변형할 수 있는 시대가 되어, 자체 문제은행이 작아도 시작 가능
- 성공하면 같은 고충을 겪는 다른 선생님들에게 판매할 길도 열려 있음

## 2. 사용자 페르소나

### 2.1 주요 페르소나

| 항목 | 내용 |
|------|------|
| 이름/별칭 | "매일 출제하는 원장님" |
| 직업 | 동네 수학학원 원장 겸 강사 |
| 핵심 니즈 | 진도에 맞는 균형 잡힌 테스트를 **매일, 빠르게** 준비하는 것 |
| 불편 포인트 | 문제 선정 시간, 난이도 균형, 매일 반복, 학생별 진도 관리 |
| 사용 상황 | 수업 직전(그날 테스트 출력), 수업 직후(진도 입력), 주말(한 주치 준비), 시험 기간(집중 출제) |
| 사용 환경 | 학원 데스크의 PC (프린터 연결) |

**보조 사용자**: 동료 강사 1~2명 — 같은 방식으로 자기 반의 테스트를 뽑는다. (검증 파트너 겸)

### 2.2 페르소나의 하루 (시나리오)

> 오후 4시, 중2 반 수업 30분 전. 원장님은 PC에서 오늘의수학에 접속한다.
> 메인 화면에 "중2-A반 일일테스트 준비됨"이 떠 있다. 어제 수업 후 "일차함수 그래프까지"라고
> 진도를 입력해 뒀기 때문이다. 문제 8개를 훑어본다 — 난이도 배분이 적당하다.
> 3번 문제가 어제 푼 문제와 비슷해 보여 [교체]를 누르니 새 문제로 바뀐다.
> [인쇄]를 누르고 프린터에서 시험지와 답안지를 꺼낸다. 여기까지 4분.
> 수업이 끝나고 "일차함수 활용 절반까지"로 진도를 갱신한다. 내일 테스트는 이미 준비되고 있다.

## 3. 사용자 스토리

### FEAT-0: 공통 흐름 (온보딩/로그인)
- [ ] 강사로서, 이메일로 간편하게 가입할 수 있어야 한다. 왜냐하면 복잡한 가입 절차는 도구 사용의 문턱이 되기 때문이다. (구글 계정 가입은 2026-08-14 원장님 지시로 제외)
- [ ] 강사로서, 로그인 상태가 유지되어야 한다. 왜냐하면 매일 쓰는 도구에서 매번 로그인하는 것은 시간 낭비이기 때문이다.

### FEAT-1: 진도 기반 자동 출제 (MVP 심장)
- [ ] 원장으로서, 반(또는 학생)의 진도를 입력하면 그에 맞는 일일테스트가 자동으로 구성되어야 한다. 왜냐하면 문제를 고르는 수고가 이 서비스의 존재 이유이기 때문이다.
- [ ] 원장으로서, 자동 구성된 테스트의 문제를 검수하고 마음에 안 드는 문제를 1클릭으로 교체할 수 있어야 한다. 왜냐하면 최종 품질 책임은 강사에게 있기 때문이다.
- [ ] 원장으로서, 일일테스트와 확인테스트(범위 복습형)를 구분해 출제할 수 있어야 한다. 왜냐하면 두 테스트의 목적(당일 확인 vs 누적 점검)이 다르기 때문이다.
- [ ] 원장으로서, 최근에 출제한 문제가 반복 출제되지 않아야 한다. 왜냐하면 학생이 답을 외워버리면 테스트의 의미가 없기 때문이다.

### FEAT-2: 난이도/유형 자동 균형 (MVP 포함 — FEAT-1의 품질 담당)
- [ ] 원장으로서, 생성된 테스트가 쉬움/보통/어려움 비율과 유형 배분을 자동으로 지키길 원한다. 왜냐하면 균형 없는 자동 출제는 수작업보다 못하기 때문이다.
- [ ] 원장으로서, 기본 난이도 배분을 반/학생 수준에 맞게 조절할 수 있어야 한다. 왜냐하면 상위반과 기초반의 적정 난이도는 다르기 때문이다.

### FEAT-3: 시험지 출력 (MVP 포함 — 결과물 담당)
- [ ] 원장으로서, 완성된 테스트를 A4 시험지 형태로 인쇄할 수 있어야 한다. 왜냐하면 수업은 종이 시험지로 진행되기 때문이다.
- [ ] 원장으로서, 답안지(정답+풀이)를 함께 출력할 수 있어야 한다. 왜냐하면 채점과 해설에 필요하기 때문이다.
- [ ] 원장으로서, 수식·도형 기호가 깨지지 않는 인쇄 품질을 보장받아야 한다. 왜냐하면 수학 시험지에서 수식이 깨지면 쓸 수 없기 때문이다.

### FEAT-4: 학생/반별 진도 관리 (MVP 포함 — 데이터 기반)
- [ ] 원장으로서, 반과 학생을 등록하고 각각의 현재 진도를 기록할 수 있어야 한다. 왜냐하면 진도 데이터가 있어야 자동 출제가 가능하기 때문이다.
- [ ] 원장으로서, 수업 후 진도를 갱신하면 다음 테스트에 자동 반영되어야 한다. 왜냐하면 진도 입력→출제 예약이 하나의 흐름이기 때문이다.

### FEAT-5: 문제은행 관리 (MVP 축소 버전 포함)
- [ ] 원장으로서, 보유한 문제(자작·기출)를 직접 등록할 수 있어야 한다. 왜냐하면 검증된 좋은 문제를 재사용하는 것이 품질의 기반이기 때문이다.
- [ ] 원장으로서, 기존 문제의 숫자·조건을 바꾼 변형 문제를 AI로 생성할 수 있어야 한다. 왜냐하면 좋은 문제 하나로 여러 번 출제할 수 있기 때문이다.
- [ ] 원장으로서, AI가 진도·난이도에 맞는 새 문제를 생성하게 할 수 있어야 한다. 왜냐하면 문제은행이 부족한 단원도 커버해야 하기 때문이다.

- [ ] 학부모 공유 (카카오톡 알림 등)

## 5. 범위 관리

### 5.1 MVP (반드시 포함)
- FEAT-1: 진도 기반 자동 출제 (심장)
- FEAT-2: 난이도/유형 자동 균형
- FEAT-3: 시험지 출력 (인쇄/PDF)
- FEAT-4: 학생/반별 진도 관리
- FEAT-5: 문제은행 관리 (등록/AI 생성/변형 — 최소 형태)
- FEAT-0: 이메일/비밀번호 로그인 (소셜 로그인 없음)

### 5.2 옵션 (시간 허용 시)
- 시험 기간 대비 범위 지정 집중 출제
- 한 주치 테스트 일괄 생성

### 5.3 Non-goals (명시적 제외)
- **학생용 앱/화면** — 사용자는 강사뿐. 학생은 종이 시험지로 만난다
- **자동 채점/성적 분석** — v2. MVP는 "출제"에 집중
- **모바일 앱** — PC 웹 중심. 모바일은 나중에
- **결제/구독 시스템** — 지금은 우리 학원용. 구조만 확장 가능하게
- **수학 외 과목** — 수학 전용으로 설계

## 7. 해결 가설과 실험

### 7.1 가설

> 만약 진도 입력만으로 균형 잡힌 테스트가 자동 완성되면, 매일 30분~1시간이 절약되고
> 테스트 품질이 일관돼질 것이다. 왜냐하면 출제 작업의 대부분이 "찾기·고르기·균형 맞추기"라는
> 기계적 작업이기 때문이다.

### 7.2 실험 루프

```
실험 → 관측 → 학습 → 다음 가설
```

| 단계 | 내용 |
|------|------|
| 실험 | MVP를 원장님 본인 수업에 2주간 실전 투입 + 동료 강사 1~2명 사용 |
| 관측 | 실사용 일수, 출제 소요 시간, 무수정 사용률, 수작업 복귀 여부 |
| 학습 | "주 5일 사용 + 수작업 미복귀"면 성공. 3일 미만이면 원인 인터뷰 |
| 다음 | 성공 시: 확인테스트 고도화 → 채점 기록(v2). 실패 시: 병목 지점(품질? 입력? 인쇄?) 개선 |
