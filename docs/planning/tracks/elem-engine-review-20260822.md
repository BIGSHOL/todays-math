## 「쉼표 나열」을 「둘 다」로 읽어 **두 번** 거짓 경보를 냈다 (2026-08-22)

조건 가드가 멀쩡한 생성기를 두 번 걸었다. 둘 다 뿌리가 같다 —
**소단원 이름은 대안의 나열인데 조건의 곱으로 읽었다.**

1. `초4 2-3-1 소수 두 자리 수**, 세 자리 수** 알아보기` → 3자리 산출 6/8 을 위반으로 걸었다.
2. `초6 2-1-5 (가분수)÷(분수)**,** (대분수)÷(분수)` → 가분수만 낸 5/8 을 위반으로 걸었다.

첫 번째는 `when` 을 하나 붙여 막았는데 **두 번째가 또 났다.** 그때 고칠 것이 문턱이
아니라 **축**임을 알았다(CLAUDE.md 2026-08-18 「문턱을 여러 번 고치게 되면 문턱이 아니라
축이 틀린 것이다」). 가르는 것은 **구조**다:

- **괄호 안 피연산자** `(세 자리 수)×(한 자리 수)` → **둘 다** 있어야 한다
- **쉼표 나열** `두 자리 수, 세 자리 수` → **어느 쪽이든** 좋다
- 조건을 하나도 안 걸치는 대안(`받아올림이 없는`)은 **세지 않는다** — 세면 늘 참이라
  그 소단원이 통째로 사각지대가 된다

그리고 「진분수와 가분수 알아보기」·「대분수 알아보기」는 서로를 끄는 `when` 때문에
**검사가 하나도 안 붙고 있었다.** 조용히 통과하던 자리다. 약한 검사(분수가 있기는 한가)를
붙여 사각지대를 없앴다.

## 세 번째 가드 — **정답이 맞는가** (2026-08-22)

미판정 16건을 눈으로 훑다가 `초6 1-3-1 (소수)÷(자연수)` 의 정답이
**몫이 아니라 나누는 수**로 나오는 것을 봤다(`27.2\div4` → `4`).

**앞의 두 가드는 이것을 구조적으로 못 본다** — 표기는 완벽하고(모두 KaTeX),
소단원 조건도 지킨다(소수를 자연수로 나눈다). 값만 틀렸다. 스스로 신고하지 않는다.

→ `probe-elem-arithmetic.ts`. 발문의 `$A op B=\square$` 를 **유리수로 정확히**
계산해 정답과 맞댄다(부동소수 금지 — `0.1+0.2 !== 0.3` 이 판정을 흔들면 안 된다).
`=\square` 가 아닌 발문은 **일부러 안 읽는다**: 「$\frac23\div\frac56$ 을 곱셈식으로
나타내시오」의 정답은 몫이 아니다. 대면 멀쩡한 문항이 빨개진다.
그래서 **「못 읽음」을 반드시 센다**(59 읽음 / 171 못 읽음).

## 하네스가 **남의 파일을 제자리 변이**시킨다 — 표시를 남겨라 (2026-08-22)

변이 하네스는 대상 파일을 **일부러 망가뜨렸다가** 되돌린다. 다중 세션 워크트리에서
그 사이 그 파일을 읽은 세션은 **「누가 내 파일을 고쳤다」**로 읽는다. 하루에 두 번 났다 —
elem-g4 가 주입된 `marks: true` 를, elem-figures 가 점선 없는 중간 상태를 봤다.

→ **도는 동안 표시 파일을 남긴다.** 이상한 것을 본 세션이 볼 자리가 있어야 한다.

**표지는 저장소 뿌리에 `MUTATION-IN-PROGRESS.<하네스이름>.txt`** 로 둔다.

- **뿌리**: `scripts/qa/` 와 `scripts/figure/` 로 갈리면 **상대는 자기 쪽만 본다**
  (실제로 그렇게 갈려 있었다). 뿌리면 `git status` 에도 뜬다.
- **하네스 이름 접미사**: 둘이 동시에 돌면 서로 덮어쓴다.
  `ls MUTATION-IN-PROGRESS.*` 한 줄로 **도는 것 전부**가 보인다.

### 그리고 **표지를 기다리는 코드가 거꾸로 걸렸다** (2026-08-22)

표지가 걷히기를 기다리는 대기를 이렇게 썼다:

```bash
if ls MUTATION-IN-PROGRESS.* scripts/figure/MUTATION-IN-PROGRESS.txt … >/dev/null 2>&1
then 도는중; else 조용함; fi
```

**`ls` 는 인자가 하나라도 없으면 실패한다.** 뿌리 표지가 없고 그림 표지가 **있어도** 실패 →
「조용함」. 그래서 **표지가 떠 있는데 「120초 조용했다」고 알렸다.**
그대로 커밋했으면 **일부러 망가뜨린 파일이 공유 이력에 실렸다.**

이 원장이 종일 적어 온 「가드가 거꾸로 걸린다」와 **똑같은 부류**이고,
**내가 만든 가드에서 났다.** 잡은 것은 「알림을 받고도 `ls` 로 한 번 더 확인한」 습관뿐이다.

→ `scripts/qa/wait-mutations-quiet.sh` 로 빼고 **자체 눈금**을 붙였다 —
**있는 표지를 찾는가**(양성) · **지운 표지를 지어내지 않는가**(음성).
표지 자리는 `[ -e ]` 로 **하나씩** 본다. 여러 인자를 한 명령에 넘기면
**그 명령의 실패 규칙이 판정을 대신한다.**

표시에는 **대상 파일 · 주인 세션 · 시작 시각 · PID** 를 적고, 「그 파일에서 측정하지 마라 ·
빨강을 보고하지 마라 · 관문 수치를 적지 마라」를 함께 적는다.

**PID 가 왜 필요한가** — 하네스가 비정상 종료하면 **표시만 남는다.** 그러면 아무도 안 도는데
다들 기다린다. 살았는지는 `kill -0 $PID` 로 보라. **프로세스를 «이름으로» 세지 마라** —
elem-g4 가 `ps -ef | grep '…\.sh$'` 로 셌는데 **`$` 앵커 때문에 0** 이 나와 「죽었다」고
판단하고 **도는 하네스 밑에서 파일을 고칠 뻔했다.** 「프로세스가 없다」의 근거가
자기 grep 패턴이었다 — 이 원장이 여러 번 적은 「«없다»의 근거가 무엇인가」 그 자리다.

**실제로 세 사람을 멈춰 세웠다** — 최종 관문을 돌리려던 나, 「초4 가 깨졌다」를 올리려던
elem-g5, 「관문 2건 빨강」을 최종 수치로 적으려던 elem-g4. 셋 다 **일부러 망가뜨린 상태**를
결과로 적을 뻔했다.
그게 없었으면 **일부러 망가뜨린 상태를 「최종 결과」로 적을 뻔했다.**

## 네 번째 가드 — **갈래가 죽었는데 셋 다 초록이다** (2026-08-22)

elem-g5 가 실물로 겪었다:

```ts
"반올림 알아보기와 어림의 활용".includes("올림")  //  ← true
```

「반올림」소단원이 **「올림」갈래로 샜다.** 올림도 반올림도 **계산은 맞으니**
표기·조건·산술 **세 가드가 전부 초록**이었다. 문항이 통째로 다른 종류로 나가는데
어느 지표에도 안 나타난다 — **변이 시험으로만** 드러났다.

→ `scripts/qa/probe-elem-routing.ts`. 생성기 원문에서 `s.includes("…")` 낱말을
**함수별로** 뽑아, 짧은 낱말이 긴 낱말보다 **먼저** 판정되는 짝을 찾는다.
낱말 **137개** 훑어 g3~g6 **죽은 갈래 0**.

> ⚠️ **만들다가 내가 그 함정에 빠졌다.** 처음엔 함수 경계를 안 보고 파일 전체를 한
> 덩어리로 읽어 **8건**이 잡혔는데 열어 보니 **전부 거짓**이었다 —
> `includes("소수")` 는 `reduce()`, `(1보다 작은 소수)×(자연수)` 는 `decMul()` 이라
> **경쟁하지 않는다.** 그대로 보냈으면 g5 가 방금 고친 2-4-* 를 다시 뜯게 했을 것이다.
> 눈금에 **「다른 함수라 서로를 못 막는다」음성 대조군**을 넣어 잠갔다(양성 1 · 음성 3).
