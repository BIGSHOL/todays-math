# 그림 인쇄 크기 트랙 — 작업 지시서 (워크트리 `그림인쇄` / 브랜치 `feat/figure-print-size`)

> 같이 읽을 것: `docs/planning/tracks/figure-quality-brief.md` §9 · §13 · §14.
> **§14 가 이 트랙이 존재하는 이유다.**

## 0. 무엇이 문제인가 — 지금 지면은 «픽셀»로 크기를 정한다

`src/lib/printOverflow.ts:157`

```ts
const scale = figure ? Math.min(1, figureMaxWidth / figure.width) : 1;
```

`src/components/math/ProblemContent.tsx:74, 92`

```
className="mt-3 max-w-[360px] print:max-w-[70mm] …"
className="h-auto w-auto max-w-full sm:max-w-[360px] print:max-w-[70mm]"
```

즉 지금 규칙은 **「픽셀 폭이 264.567(=70mm)을 넘으면 70mm 로 줄이고, 아니면 픽셀
그대로(96dpi)」** 뿐이다. **「얼마로 그린다」가 없다.**

### 이게 왜 결함인가 (실측)

- 원본 가로 픽셀이 **41px ~ 7,343px** (중앙 425). 큰 그림은 70mm, 작은 그림은 작은 채로
  나간다 — **같은 삼각형이 문항마다 다른 크기**로 인쇄된다.
- 그리고 다른 트랙이 **300dpi 로 다시 자르면 이게 터진다.** 지금 200px 인 그림은
  96dpi 로 작게 나가는데, 다시 자르면 600px 이 되어 264 를 넘고 **70mm 로 확대**된다.
  자르기만 고치면 **지면의 그림 크기가 통째로 달라진다.**

원장님 지시(2026-08-19): 「모든 그림이나 도형 크기가 **일관성이 있어야**하니까」.

## 1. 이 트랙이 할 일 — **인쇄가 물리 크기(mm)를 보게 한다**

규격(§9):

```
목표 인쇄 폭(mm) = min(70, 원본 rect 폭(pt) / 72 * 25.4)
```

원본 지면에서 그 그림이 차지하던 물리 크기가 곧 출제자가 정한 크기다. 그걸 그대로 쓴다.

### 🔴 «물리 크기»는 아직 데이터에 없다 — 그래서 **계약을 먼저 만든다**

`figure-manifest.json` 에 `rect` 키가 **0건**이고, RPM 의 `source_coords` 는 발문 상자다
(§13). 그림 칸은 `map_exam()`·`figure_rect()` 가 런타임에 만들고 **버린다.**
그 값을 되찾아 원장으로 만드는 일은 **`그림벡터` 트랙이 맡는다** —
산출물은 `scripts/qa/reports/figure-rect-ledger.json` 이고, 그림마다 `width_mm` 이 있다.

**너는 그 파일을 기다리지 마라.** 네가 할 일은 **지면 쪽이 mm 를 받을 수 있게 만드는
것**이다. 값이 없을 때는 **지금 동작을 그대로** 해야 한다(회귀 0).

1. 그림마다 「인쇄 폭(mm)」을 들고 다닐 **자리**를 정하고(별도 컬럼 / `figureDims` 확장 /
   별도 대장 중 하나) 왜 그걸 골랐는지 근거를 적어라.
   ⚠️ `problem.figure_dims` 는 지금 **평탄 배열 `[w1,h1,w2,h2,…]` 픽셀**이다
   (`parseFigureDimensions`, `printOverflow.ts:106`). 여기에 mm 를 섞으면 길이 검사
   (`flat.length !== figureCount * 2`)가 조용히 무너진다 — 섞을 거면 그 검사부터 고쳐라.
2. `estimateFigureBlockPx` 가 **mm 를 알면 mm 로, 모르면 지금처럼 픽셀로** 재게 한다.
3. 화면/지면 컴포넌트(`ProblemContent.tsx`)가 mm 를 알면 `width: Xmm` 로 그리게 한다.
   ⚠️ **인라인 `style` 은 Tailwind 를 이긴다.** 예전에 카드 폭을 인라인으로 박았다가
   `print:w-auto` 가 죽어 인쇄가 깨진 적이 있다. 인쇄 규칙과 어떻게 겹치는지 확인하고
   테스트로 잠가라.
4. **자와 지면이 한 숫자를 쓰게** 하라. 규칙이 두 벌이 되면 한쪽만 옮겨도 아무도 모른다.
   (실제 사고: 해설 자에만 「세로 수식」 항을 넣고 문제지 자에 안 넣어 놓침이 17.6% 였다.)

## 2. 🔴 이건 «지면을 바꾸는» 일이다 — 완료 조건이 다르다

- **절대 규칙 6**: 인쇄 관련 변경은 **실물 프린터 출력 검수까지가 완료 조건**이다.
  네가 「완료」라고 선언하지 마라. 대신 **`/dev/print-check` 에 항목을 추가**해라 —
  목록 SSOT 는 `src/app/dev/print-check/items.ts` 이고, `status` 는 `"통과"` 로
  **바꾸지 마라**(원장님이 실물로 보시고 바꾼다).
- **D-07**: 형태를 결정하는 변경은 원장님 확정이 필요하다. 「그림 크기 규칙」은 원장님이
  방향(일관성)을 이미 지시하셨지만, **실제 지면이 어떻게 보이는지는 원장님이 보셔야 한다.**
  그래서 **전후 비교 지면을 만들어라** — 같은 시험지를 지금 규칙 / 새 규칙으로 각각
  뽑아 나란히 볼 수 있게. `docs/design/mockups/` 에 이미 그런 지면들이 있다.

## 3. 🔴 이 저장소에서 반드시 지킬 것

1. **`git add -A` 금지.** 다른 오르카 세션이 같은 저장소를 쓴다. **경로로만** 스테이징하고
   커밋은 만들자마자 하라(스테이징한 채로 두어 남의 커밋에 실려 나간 전례가 두 번 있다).
2. **TDD** — RED→GREEN. 테스트 없이 구현하지 마라(절대 규칙 2).
3. **공유 DB(D-31) 에 쓰지 마라.** 읽기만. 스키마를 바꿔야 하면 **마이그레이션 파일만
   만들고 적용하지 마라** — 보고서에 적고 멈춰라.
4. **`fs.rmSync` 금지** — 경로에 한글이 있으면 노드가 **메시지 없이** 죽는다
   (`noRmSync.test.ts` 가 막는다).
5. **마우스 어포던스(D-30)** — `npm run lint:affordance` 를 통과해야 한다. 우회 금지.
6. 커밋 전에 **직접** `npm run lint` · `npm run type-check` · `npm run test` 를 돌려라.
   훅을 믿지 마라 — 새 워크트리에서 훅이 **조용히 안 돌던** 전례가 있다.

## 5. 이 저장소가 여러 번 데인 함정

- **가드는 망가뜨려 봐야 가드인 줄 안다.** 넣은 검사를 하나씩 변이시켜 **빨개지는지**
  확인하라. 안 빨개지면 장식이다(28개 전부 초록이던 전례가 있다).
- **지표의 «참»이 제품 상수에서 오면 안 된다.** 실측값에서 와야 한다.
- **같은 규칙을 쓰는 자리가 둘이면 한 숫자를 두 곳이 쓰게** 하고, 한쪽만 옮기면
  빨개지는 테스트를 같이 둬라.
- **「N개 통과」는 N이 전부인지 말해 주지 않는다.** 분모를 먼저 지켜라.
