# 트랙 D — HWP 원본 재추출 (뒤늦게 열린 정본 경로)

`docs/planning/tracks/README.md` 의 공통 규칙을 먼저 읽어라. 그 규칙이 이 문서보다 우선한다.

## 발견 — 본문을 PDF 에서 뽑을 이유가 처음부터 없었다

`scripts/qa/extract-final-batch.py` 를 보면

- **180행** `doc = textlayer.extract(pathlib.Path(p["pdf"]))` — 본문은 **PDF 텍스트 레이어**
- **186행** `answers = hwp_answers(p["hwp"], work)` — HWP 는 **정답만**

그런데 `scripts/vendor/testchanger/hwp_extract.py` 를 직접 돌려 보면 문항마다
`stem` · `choices` · `answer` · `topic`(소단원) · `score`(배점) · `type` · `solution`(해설)
이 **전부** 나온다. 한컴오피스 COM 도 이 컴퓨터에서 동작한다(2026-08-16 확인).

```
python scripts/vendor/testchanger/hwp_extract.py "<hwp 경로>" -o out.json
```

완료본 짝 2,950편 중 **2,944편에 HWP 가 있다**(`scripts/qa/reports/final-pairs.json`).

## 이게 왜 중요한가 — 원장님이 직접 짚은 세 건

| 문항 | 폐기 목록의 판정 | 실제 |
|------|------------------|------|
| 국제고 2697 | "본문 결손" 2건 | 원본은 8문항. DB 2건이 **둘 다 해설 지면 텍스트** |
| 강북고 2928-19 | "해설만 들어 있음" | 문제는 PDF 4쪽에 멀쩡. **1~12번 본문은 통째로 "정답" 두 글자** |
| 현풍고 2900-18 | "원본 모순 — OCR 훼손" | **훼손 아님.** HWP 원문 그대로. 판정이 틀렸다 |

원인은 하나다. PDF 뒤쪽 해설 지면에도 `1.` `2.` 줄머리가 있는데 추출기가 **뒤에 나온 것을
남겨서** 해설이 앞쪽 문제를 덮었다. (같은 성질의 버그를 `extract-official-answers.py`
에서 이미 한 번 잡았다 — 그 주석을 읽어라.)

## 규모는 부풀리지 마라 — 실측

표본 25편에서 **문항 개수는 HWP 520 vs PDF 513 으로 거의 같다.** 24/25 편은 개수가 정확히
일치했다. **대부분의 시험지는 PDF 경로로도 제대로 나왔다.** 강북고·국제고 같은 붕괴는 소수다.

HWP 의 값어치는 개수가 아니라 **수식의 온전함**이다. PDF 경로가 만들어 낸 실제 훼손:

```
f(x)=∈∉⊂^{∩}_{∩}(ax-an)/(x-2) ...      ← 경우 나눔 중괄호가 PUA 쓰레기로
\frac{2227777}{45_{2}(6×6×6)(5+5+5+5)}  ← 쌓인 식이 분수로 뭉개짐
```

폐기 후보 515건 중 **215건이 HWP 원본을 갖고 있다**: 수식 훼손 80 중 52,
증명·작도형 74 중 72(HWP `solution` 이 "해설참조" 를 대체할 수 있다), 해설지 적재 8 전부,
본문 결손 54 중 25, 그림 없음 285 중 46.

## 할 일

### D-1. 전량 HWP 추출 — 토큰 0, 오래 걸린다. 먼저 걸어 둬라

2,944편을 `hwp_extract.py` 로 뽑아 `scripts/qa/reports/hwp/<examId>.json` 에 쌓아라.
HWP COM 은 단일 인스턴스라 병렬이 잘 안 될 수 있다 — 먼저 10편으로 소요를 재고,
병렬이 되는지 확인한 뒤 규모를 정해라. 재개 가능해야 한다(이미 있는 파일은 건너뛴다).
**진행 상황을 주기적으로 보고해라.** 사람이 지켜볼 수 있어야 한다.

### D-2. 어느 문항이 PDF 때문에 망가졌는지 판정하라 — **여기가 핵심**

전부 갈아엎지 마라. **HWP 가 확실히 나은 것만** 교체한다. 판정 근거를 규칙으로 세워라.
확실한 신호부터:

- DB 본문이 30자 미만 (실측 24건 — 강북고 12건 포함)
- DB 본문에 해설 냄새(`따라서` `이므로` `대입하면` `위의 식`)가 짙은데 문제 냄새가 없다
- DB 본문에 PUA 잔재(`∈∉⊂` 연쇄, `\ue0` 계열)나 뭉개진 분수
- HWP 문항 수 > DB 행 수 (국제고 8 vs 2)
- HWP `stem` 과 DB 본문의 유사도가 바닥

**반대 방향도 반드시 보라**: HWP 쪽이 더 나쁜 경우가 있는지. 예컨대 워터마크가 본문
가운데 끼어드는 걸 실측했다(현풍고 18번 stem 안에 `대구광역시 내신 수학 연구회`).
교체가 개선인지 개악인지 **표본 30건을 눈으로 확인**하고 숫자를 내라.

### D-3. 수식 표기를 맞춰라

HWP 는 한글 수식 스크립트로 준다 (`int _{} ^{} {...}`, `LEFT (`, `over`, `pi`).
DB 는 KaTeX 가 읽는 `$...$` LaTeX 다. **변환기 없이 그대로 넣으면 지면이 깨진다.**
testchanger 에 이미 변환 로직이 있는지 먼저 찾아라(`scripts/vendor/testchanger/`,
`F:\시험지변환기`). 없으면 만들되, `renderKatexSafe` 기준으로 **렌더 성공률을 측정**해라.
CLAUDE.md 의 KaTeX 교훈(unknown command 가 `.katex-error` 가 아니라 `#cc0000` 으로 난다)을
반드시 읽어라.

### D-4. 덤으로 열리는 것들 — 확인만 하고 해당 트랙에 넘겨라

- **소단원(`topic`)**: 표본 25편 중 HWP 에 topic 이 있는 건 520 중 162. 폴더마다 갈린다
  (10-handoff.md B단계 기록과 일치). 지금 매핑이 빈 문항을 채울 수 있는지 세어만 봐라.
- **배점(`score`) · 유형(`type`)**: `problemType='서술형'` 라벨이 못 미더웠던 문제
  (실측 95% 가 `[서술형 N]` 배점 머리표였다)를 여기서 정본으로 바로잡을 수 있다.
- **해설(`solution`)**: 증명·작도형 72건의 "해설참조" 를 대체할 수 있다 → 트랙 B 에 넘겨라.
- **그림**: HWPX 는 zip 이고 `BinData` 에 원본 이미지가 들어 있다. PDF 오려내기보다
  정확할 수 있다 → **트랙 A 에 넘겨라.** 직접 손대지 마라.

## 완료 기준

- HWP 추출 N / 2,944 편, 실패 사유별 집계.
- 「교체 대상 M 건 / 그대로 둘 것 K 건」이 규칙과 표본 검증으로 갈렸는지.
- 교체 후 KaTeX 렌더 성공률이 **떨어지지 않았음**을 숫자로.
- 폐기 후보 515건 중 몇 건이 되살아났는지.
- 쓰는 컬럼은 `content` `choices` `problemType` 뿐. `answer` 는 트랙 B, `figureUrls` 는
  트랙 A, `externalId` 는 트랙 C 소관이다 — **넘겨라, 직접 쓰지 마라.**
- dry-run 기본 + `ALLOW_SHARED_IMPORT=1` 게이트. 되돌릴 수 있게 교체 전 본문을 백업해라
  (`scripts/qa/backup-transformed-content.ts` 가 선례다).

### 되풀이하지 말 것 — 가드를 거꾸로 건 것이 다섯 번

전부 같은 실수였다. **DB 의 손상 자체를 "DB 가 충실하다" 는 증거로 읽었다.**

1. **정렬**: "유사도 중앙값이 낮으면 정렬 실패 → 편 통째 제외" 로 걸었더니
   **손상이 가장 심한 2928·2697 이 먼저 버려졌다.** 손상될수록 유사도가 낮으니 당연하다.
   → **다른 오프셋이 0보다 뚜렷이 나을 때만** 어긋난 것으로 본다. 근거는 본문 유사도
   말고 **배점·정답 일치**(본문과 독립)를 같이 센다. 2928 은 offset 0 의 유사도 합이
   나머지의 3배였다 — 정렬은 옳았다.
2. **길이**: "HWP 가 짧으면 열위" 로 막았더니 **해설이 문제보다 길다**는 당연한 사실에
   걸렸다(2928-19: DB 723자=해설, HWP 321자=문제). → 해설/발문 냄새를 **양쪽 비교**한
   뒤에만 길이 가드를 적용한다.
3. **한글 길이**: "HWP 한글이 6자 미만이면 빈약" → `$\sum_{k=1}^{9}a_k=12$ 일 때 …
   의 값은?` 같은 **수식 위주 문항은 원래 한글이 몇 자뿐**이다. DB 가 Σ 를 통째로 잃은
   문항이 이 조건에 걸려 보류로 내려갔다.
4. **오염된 길이**: DB 가 긴 이유가 옆 문항 해설·머리말이 딸려 들어와서인데, 그 길이로
   H3 를 재니 **오염이 심할수록 교체가 막혔다.** → **발문끼리만** 견준다.
5. **증거를 지웠다**: HWP 에도 지면 머리말이 있는 편이 있어 `학원로고` 줄을 지웠더니,
   **차단 근거만 사라지고** `달서고 2학년 수학1`·강사 이름 줄은 그대로 들어갔다.
   → 지우지 말고 `H12` 로 **막는다**.

### 거짓 음성 사냥이 제일 값어치 있었다 — 교체 1.4% → 13.7%

「유지」를 유사도 낮은 순으로 눈으로 보니 한 무리가 통째로 새고 있었다.

```
DB  : <상자> ⁄ • $26+26$ • $42+42+42+42$      ← 원본은 (4²+4²+4²+4²)/(2⁶+2⁶)
DB  : 정규분포 N $(m,^{2})$                    ← σ 가 사라졌다
DB  : $\frac{a-c}{b}$                          ← 원본은 $a-\frac{c}{b}$ (다른 식이다)
```

지수·분수가 사라졌는데 **한글 지문은 멀쩡해 유사도가 0.56 으로 높았다.**
지문 유사도로는 수식 훼손을 못 잡는다. 훼손 문자 자체를 봐야 한다.

## D-3. 수식 표기 — **잔재 1.98% → 0.06%**

변환기는 **새로 만들지 않았다.** testchanger `core/hwpeq_to_latex.py` 를 그대로 쓰고
(그쪽은 `latex_to_hwpeq` 와의 왕복으로 정합성을 재고 있다), 저장소는 **한 바이트도
고치지 않고** 앞뒤에 전처리·후처리만 붙였다(`scripts/qa/hwpeq_unglue.py`).

| | 적용 전 | 적용 후 |
|---|---|---|
| 잔재 (수식 span 678,433 기준) | 1.98% | **0.06%** |
| 잔재 (문항 69,703 기준) | 8.06% | **0.34%** |
| `\mathrm{barAD}` 형태 | 2.68% | **0.01%** |

고친 것: 붙어버린 구조 키워드(`1over5x` → `\frac{1}{5}x`), `of` 짝 없는 `root` 는
제곱근(`3root3` → `3\sqrt{3}`), 대소문자 무관 `rm`/`it` 접두 분리(`rmbarAD` →
`\mathrm{\overline{AD}}`), 미변환 키워드(`BOX`·`DIVIDE`·`!=`).

### ⚠️ KaTeX 렌더 실패율로는 이걸 못 잡는다

`1over5x` 를 KaTeX 는 **에러로 보지 않는다.** 그냥 글자로 그린다. 그래서 실패율은
0.1% 로 멀쩡했고 **표본을 눈으로 보고서야** 드러났다(10-handoff §8.5 의 "동어반복 측정"
과 같은 함정). 별도 지표가 필요하다 — `scripts/qa/measure-hwp-latex-residue.py`.

**렌더 성공률은 떨어지지 않았다.** 교체 대상 4,069행만 놓고 재면

| | 값 |
|---|---|
| 교체 전 KaTeX 실패 | 1,923 / 38,696 (**4.97%**) |
| 교체 후 KaTeX 실패 | 64 / 46,313 (**0.14%**) |

전량 기준으로도 DB 0.7% vs HWP 0.4% 로 HWP 가 낫다.

### 트랙 A 에게 — `.hwpx` 를 두 번 변환하지 마라

`.hwpx` 변환은 한컴 COM 단일 인스턴스라 편당 약 12.8초, 전량이면 10.5시간이다.
D-1 이 이미 다 했으니 **그대로 읽어라**. 경로는 `scripts/qa/reports/hwpx/<examId>.hwpx`.

**전수 검증했다** (`python scripts/qa/verify-hwpx.py` 로 재현, COM 불필요):

| | 값 |
|---|---|
| 파일 | **3,302편 · 손상 0** (전부 ZIP 으로 열리고 `Contents/section*.xml` 보유) |
| 그림 보유 편 | **3,206** |
| `BinData` | **21,627장** — bmp 16,948 · png 3,587 · jpg 992 · jpeg 84 · 기타 13 |
| 디스크 | ZIP 상태 **1.8GB** · 풀면 **23.6GB** |
| 편별 명세 | `scripts/qa/reports/hwpx-manifest.json` (편당 장수·압축 전후 크기) |

**용량은 80GB 가 아니다.** `.hwpx` 는 ZIP 이라 BMP 를 이미 deflate 한다 — 압축 전
23.6GB 가 ZIP 안에서 1.6GB 다. 편당 27MB 는 **압축을 푼 뒤** 크기이고, 필요한 문항의
BinData 만 골라 풀면 그 비용은 안 든다. 그래서 png 재인코딩 없이 통째로 남겼다 —
이미지뿐 아니라 XML 좌표까지 같이 얻는다.

⚠️ 전량을 한꺼번에 풀지 마라. 그림 후보를 고른 뒤 그 편만 풀고, 저장은 png 로
재인코딩할 것(트랙 A 실측 3.4MB bmp → 439KB png).

## 적재 — 아직 쓰지 않았다

`scripts/qa/apply-hwp-replacement.ts` 는 **드라이런까지만** 돌렸다.

```bash
npx tsx scripts/qa/apply-hwp-replacement.ts                                # 드라이런
ALLOW_SHARED_IMPORT=1 npx tsx scripts/qa/apply-hwp-replacement.ts --apply  # 실제
```

- 게이트를 **PrismaClient 생성 전**에 본다. `--apply` 만 주면 접속조차 안 하고 끝난다.
- 쓰기 직전 그 행들의 `content`·`problemType` 을 통째로 백업한다. 백업이 안 써지면
  한 행도 안 건드린다.
- **판정에 쓴 스냅샷과 현재 본문이 다르면 그 행은 건너뛴다** — 공유 DB 를 트랙 넷이
  쓰므로 남이 고친 것을 덮지 않는다.
- 교체 후 KaTeX 실패율이 전보다 높으면 **중단한다.**
- 쓰는 컬럼은 `content` 뿐. `problemType` 은 `--fix-type` 일 때만(보기 4개 이상인데
  DB 가 `서술형` 인 **26행**).

## 표본 검증

**실체 있는 중간 결손 10건**과 **최종 1,077건에서 10건**을 눈으로 봤다.
20건 전부 **온전한 문항**이었다 — 발문·보기 5개·소단원·배점이 다 있고 그림도 없다.


## 남은 의문 — 원인은 아직 확정 못 했다

1,077건이 **왜** 빠졌는지는 이 트랙의 자료로는 못 밝힌다. PDF 쪽 추출 산출물
(`scripts/qa/reports/final-batch/`)이 이 컴퓨터에 없기 때문이다. 가장 유력한 가설은
**PDF 텍스트 레이어의 문항 분할이 놓쳤다**는 것이다 — 10-handoff §8.5 가 같은 성질의
결함을 이미 기록했다(*"번호가 1씩 이어질 때만 문항으로 인정해 한 번 끊기면 뒤가 통째로
안 잡힌다"*). HWP 에는 있고 PDF 경로에만 없다는 사실이 그 가설과 맞는다.

확인하려면 B단계 산출물 원본이 필요하다. **가설이지 결론이 아니다.**
