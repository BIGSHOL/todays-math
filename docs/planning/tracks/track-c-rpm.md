# 트랙 C — RPM 원본 역추적과 중복

`docs/planning/tracks/README.md` 의 공통 규칙을 먼저 읽어라. 그 규칙이 이 문서보다 우선한다.

## 왜 하나

RPM 이관분 4,862건(`source='transformed'`)에 **`externalId` 가 비어 있다.** 그래서
"이 문항이 원본 어디서 왔나" 를 물을 수 없고, 그 하나 때문에 세 가지가 막혀 있다:

1. **중복 판정** — 본문이 똑같은 233건(88그룹)이 있는데 원본에서 `printed_number` 만 다르다.
   무엇을 남길지 근거가 없다.
2. **그림 연결** — 트랙 A 의 RPM 그림 814건 회수가 본문 대조라는 약한 키에 의존한다.
3. **폐기 판단** — 폐기 후보 515건 중 원본 위치가 안 붙은 5건이 여기서 온다.

`externalId` 를 채우면 셋이 한꺼번에 열린다. 그리고 이건 **AI 토큰 0** 이다 —
sumaek 원본 DB 에 답이 이미 있다.

## 배경 — 이 이관은 이미 세 번 새고 있었다

| 결함 | 규모 | 원인 |
|------|------|------|
| 객관식 정답 유실 | 4,862 | 원본 키가 `choiceId` 인데 `id` 로 읽었다 |
| 보기 마커 ①~⑤ 유실 | 1,319 | 평문화하며 번호를 떨어뜨렸다 |
| 그림 미조회 | 1,014 | `diagram_assets` 테이블을 아예 안 봤다 |

**세 번째까지 갔는데도 테스트는 계속 초록이었다.** 내가 만든 합성 픽스처가 원본과 다른 키를
써서다. 이 트랙에서 가장 중요한 산출물은 사실 C-3 이다.

## 할 일

### C-1. `externalId` 채우기 — 먼저

sumaek 원본에서 RPM 문항 id 를 가져와 DB 4,862행에 매긴다.
`scripts/qa/recover-rpm-answers.ts` 가 이미 sumaek 을 읽고 본문으로 대조하는 로직을 갖고 있다
(`SOURCE_SELECT`, `toSourceRow`, `readSource` 가 export 돼 있으니 재사용해라).

⚠️ 본문 대조 키는 **적재 당시 형태와 마커 복원 형태 둘 다** 등록해야 맞는다 —
보기 마커를 나중에 복원해서 지금 DB 본문이 적재 시점과 다르다.
정확히 한 건에만 대응되는 것만 채워라. 여럿에 걸리면 미상으로 남기고 세어라.

### C-2. 중복 233건 / 88그룹 — **보고서만. 지우지 마라**

`externalId` 를 채운 뒤 그룹을 확정하고, 각 그룹에 대해
「원본 시험지·번호 / 정답 유무 / 그림 유무 / 단원 매핑 상태」를 표로 내라.
**어느 쪽을 남길지는 원장님 결정 사항이다.** 삭제도 `reviewStatus` 강등도 하지 마라.
판단 근거를 갖춘 보고서를 `docs/planning/` 아래 문서로 남기는 것까지가 이 항목의 끝이다.

권할 만한 규칙이 보이면 제안은 해라 (예: "정답+그림 둘 다 있는 쪽을 남긴다").

### C-3. 실데이터 회귀 검사 — **이 트랙의 진짜 산출물**

`scripts/qa/verify-convert-rpm.ts` 를 **sumaek 원본 표본에 직접 물리는 회귀 검사**로 굳혀라.
합성 픽스처는 이미 세 번 배신했다. 최소한 이걸 잡아야 한다:

- 원본 보기 개수 = 변환 후 보기 개수 (중복·유실 없음)
- `correctChoiceIds` → 정답 마커가 실제로 채워짐
- 보기 마커 ①~⑤ 가 본문에 살아 있음
- `diagram_assets` 가 있는 문항은 `figureUrls` 가 비지 않음
- `externalId` 가 채워짐

원본이 없는 환경에서는 **조용히 통과하지 말고 skip 을 명시**해라. 조용한 통과가 이 사달의 원인이다.

## 완료 기준

- `externalId` 채움 N / 4,862, 미상 M 건과 그 사유.
- 88그룹 판단 근거 표 (문서).
- 실데이터 회귀 검사가 지난 세 결함을 **일부러 되돌렸을 때 실제로 빨강이 되는지** 확인한 기록.
- `externalId` 외의 컬럼은 건드리지 마라. 행 삭제 금지.

## C-2. 233건 / 88그룹 — 보고서만. **한 행도 지우지 않았고 `reviewStatus` 도 안 내렸다**

→ `docs/planning/13-rpm-duplicate-groups.md`

**결론: 중복이 아니다.** 88그룹 중 **86그룹**은 원본 정답이 그룹 안에서 서로 다르다.

### 지난 결함을 일부러 되돌렸을 때 실제로 빨강이 되는지 — **확인한 기록**

`--fault` 는 운영 코드를 고치지 않는다. 변환기 소스를 **임시 사본에 망가뜨려** 불러 돌린다.
DB 쪽 결함은 그 시절의 DB 상태를 재현한다. 치환 대상이 없으면 **던진다**(조용히 통과 금지).

```
$ npx tsx scripts/qa/verify-convert-rpm.ts --fault all
── 결함 되돌리기 — 검사가 실제로 빨강이 되는지 ──

[choice-id] 원본 키가 `choiceId` 인데 `id` 로만 읽던 결함 (정답 4,862건 유실)

  → 잡음 (answer-filled, answer-marker-form)

[marker-drop] 평문화하며 보기 번호를 떨어뜨리던 결함 (마커 1,319건 유실)
  ✘ 보기 마커 ①~⑤ 가 본문에 살아 있다 — 0/1884 0.00%

[answer-flatten] `flattenStructured` 만으로 정답을 펴던 결함 (`correctChoiceIds`/`accepted` 를 못 봄)
  ✘ 원본에 정답이 있으면 변환 후에도 있다 — 0/6057 0.00%
  ✘ 객관식 정답이 보기 번호(①~⑤) 형태 — 0/1864 0.00%
  → 잡음 (answer-filled, answer-marker-form)

  ✘ 원본에 `diagram_assets` 가 있는 문항은 `figureUrls` 가 비지 않는다 — 0/931 0.00%

$ echo $?
```

**주입 도중 실제로 한 번 속았다.** 처음엔 결함마다 같은 임시 파일 이름을 덮어썼는데,
tsx 의 변환 캐시가 앞 결함의 코드를 그대로 돌려줘 `marker-drop` 이 **초록으로 통과**했다
(단독 실행하면 빨강). 결함마다 파일 이름을 달리해 고쳤다. 여기 적어 둔다 —
"검사가 초록"과 "검사가 돌았다"는 다르다.

레시피가 썩는 것도 막았다: `src/__tests__/unit/verifyConvertRpmFaults.test.ts` 가
치환 대상 문자열이 `convertRpm.ts` 에 그대로 있는지 본다(원본 없이도 돈다).
변환기를 손보면 이 테스트가 먼저 빨강이 된다.

## 코디네이터에게 넘기는 것 — 내 컬럼이 아니라 손대지 않았다

1. **RPM 단원 학년 오배정 1,364행 (29.5%).** `externalId` 를 채우고 나서야 원본 교재
   학년과 배정 단원 학년을 대조할 수 있게 됐다. 중3 교재 문항이 미적분1·공통수학1 단원에,
   중2 교재 문항이 초5 단원에 실려 있다. 원인은
   `normalizeGrade("RPM 중학 수학 2-2 (2022 개정)")` 가 `"중2"` 가 아니라 **입력을 그대로**
   돌려주는 것 — 교재 규칙 `/중([123])/` 이 `중학` 에서 안 걸린다. 그래서 `scoped` 가 비고
   `pool` 이 초1~고3 전체로 넓어진다. 기출에서 잡은 것과 같은 부류(10-handoff §3, 513건).
   **정정 도구 `fix-unit-assignments.ts` 는 `externalId` 로 행을 찾으므로 지금은 가능하다.**
   상세: `13-rpm-duplicate-groups.md` §5.
2. **233건에 `--resolve-by-solution` 을 적용할지** — 원장님 결정. 적용한다면 **트랙 A 의
   RPM 그림 회수보다 먼저** 돌려야 그림이 본문 대조 대신 키로 붙는다.
3. `12-discard-candidates.md` 의 "원본 위치가 안 붙은 5건" — `externalId` 가 붙었으니
   `build-discard-list.ts` 를 다시 돌리면 채워질 것이다(그 파일은 내 소유가 아니라 안 돌렸다).

## 트랙 D 와의 경계

C-1 의 본문 대조는 **`source='transformed'` 행에만** 건다. `past_exam` 본문은
한 번도 읽지 않는다 — 다른 source 행에서 읽는 것은 `externalId` **문자열뿐**이고
(`@unique` 충돌 차단용), 기출의 `externalId` 는 `{exam_id}-{문항번호}` 라 본문 재추출과
무관하다. 세 스크립트 모두 `where: { source: "transformed" }` 로 못박아 뒀다.

(`source` 로 먼저 가르고, RPM 은 채워진 `externalId` 로 sumaek 을 직접 조회 — 본문 대조보다 확실하다).
510/515 복구.

### 앞으로의 규칙 — 공유 DB `--apply` 전에 코디네이터에게 먼저 알린다

컬럼 소유권이 갈려 있어도 **다른 트랙이 그 컬럼의 "빈 상태"에 가정을 걸고 있을 수 있다.**
이번이 그랬다 — 트랙 C 는 제 컬럼에 제 값을 넣었는데, 그 값이 지금까지 기출에만 있었다는
사실에 기대던 코드가 깨졌다. 소유권은 **쓸 권리**를 나눌 뿐 **읽는 쪽의 가정**까지 나누지 못한다.

그래서 이 트랙은 앞으로 공유 DB 에 `--apply` 를 돌리기 전에 코디네이터에게
「어느 컬럼을 · 몇 행 · 어떤 값 모양으로」 먼저 알린다. 이번 건으로 말하면
**"`transformed` 4,629행의 `external_id` 가 NULL → UUID 가 된다"** 한 줄이면 충분했다.

> 코디네이터에게 제안: 이 문장을 `tracks/README.md` 공통 규칙 2번 옆에 넣는 게 좋겠다.
> 지금 규칙은 "쓰기를 막는" 것만 다루고 "써도 되는 걸 썼을 때 남이 깨지는" 경우를 안 다룬다.
> 그 파일은 내 소유가 아니라 손대지 않았다.

## 2. 미상 233건 — 무엇이고 왜 미상인가

### 사유는 한 가지다

미상 233건은 **전부** `ambiguous` — 우리 본문이 sumaek 원본 **두 행 이상**에 걸린다.
다른 사유는 0이다: 매칭실패(`unmatched`) 0 · 원본 점유 충돌(`contested`) 0 ·
`externalId` 선점 충돌 0. 후보가 0개인 행도 0이다.

| 원본 후보 수 | DB 행 |
|---|---|
| 2개 | 111 |
| 3개 | 33 |
| 4개 | 62 |
| 7개 | 7 |
| 8개 | 8 |
| 12개 | 12 |
| **합계** | **233** |

거꾸로도 확인했다 — **채운 4,629행 중 후보가 1개가 아닌 것은 0건**이다.
"후보 정확히 1개 ⟺ 채움" 이 빈틈없이 성립한다.

### 왜 못 채우나 — 이유 둘

1. **근거가 없다.** 후보 2~12개 중 어느 원본인지 가릴 단서가 본문에는 없다.
   찍으면 그 위에 중복 판정·그림 연결·폐기 판단이 전부 쌓인다.
2. **찍으면 옳은 행까지 막는다.** `Problem.external_id` 는 `@unique` 다.
   한 원본 id 를 엉뚱한 행이 차지하면, 나중에 진짜 주인이 나타나도 넣을 자리가 없다.

### "본문 중복 233건" 과 수가 같은 것은 우연인가 — **아니다. 같은 집합이다**

판정 규칙이 하나라서 그렇다. 채우는 조건이 「원본 후보가 정확히 하나」이므로
**후보가 둘 이상인 행 = 미상 = 기존 문서가 말하던 본문 중복** 이다.
`recover-rpm-answers.ts` 의 「본문중복 제외」도 같은 규칙이고(`keysOf` 를 그대로 공유한다),
실제로 지금 돌려도 같은 숫자가 나온다:

```
$ npx tsx scripts/qa/recover-rpm-answers.ts
본문 매칭 — 유일 4629 · 본문중복 제외 233 · 매칭실패 0
```

그래서 이 233행은 **정답도 그림도 한 건도 못 받았다**(`정답 없음 233/233 · 그림 없음 233/233`).
원인 하나가 셋을 동시에 막고 있었다는 뜻이고, 그래서 하나를 풀면 셋이 같이 풀린다.

**다만 "본문 중복" 을 좁게 —「우리 DB 본문이 글자까지 같은 행」— 으로 세면 230행 / 85그룹이다.**
차이 3건은 **우리 DB 안에서는 유일한데 원본에 쌍둥이가 있는** 행이다(원본 두 행 중 하나만 적재됨).
우리 쪽만 봐서는 안 보이고 원본을 봐야 드러난다. 기존 문서의 233/88그룹은 **원본 기준**
숫자였으므로 내 233과 정확히 같다.

## 3. 전제 정정 — 폐기 후보의 「원본 미상 5건」은 여기서 오지 않는다

트랙 C 문서 §왜 하나 3번이 "폐기 후보 515건 중 원본 위치가 안 붙은 5건이 여기서 온다"고 적었는데,
**확인해 보니 아니다.** 그 5건이 실린 소단원에 내 미상 233건은 **한 건도 없다**:

| 폐기 문서의 「원본 미상」 소단원 | 내 미상 233 중 | 그 소단원의 `source` 분포 |
|---|---|---|
| 중1 / 정수와 유리수 | **0건** | transformed 209 · past_exam 831 |
| 공통수학1 / 인수분해가 되지 않는 연립이차방정식 | **0건** | transformed 96 · past_exam 181 |
| 중1 / 최대공약수와 최소공배수의 활용 | **0건** | manual 7 · past_exam **294** (transformed 0) |

마지막 줄이 결정적이다 — 그 소단원에는 `transformed` 행이 **아예 없다**. RPM 일 수가 없다.
사유 설명("식이 OCR로 훼손", "본문 결손(문항 내용 없음)")도 기출 추출 쪽 증상이다.
**이 5건은 트랙 B/D 소관이지 트랙 C 가 풀 수 있는 것이 아니다.**

반대로 폐기 후보에 든 RPM 행들은 `bb6c226` 이후 「후보 N곳 (0039, 0040, 0041)」처럼
**후보 목록**으로 나온다. 그것들이 곧 내 233건이다. 여기에
`--resolve-by-solution` 을 적용하면 **214행이 후보 하나로 확정**되어 폐기 문서의
「후보 N곳」이 「정확히 이 번호」로 바뀐다. 원장님 승인이 나면 폐기 판단의 정밀도가 같이 올라간다.

## 2. 새로 드러난 것 — 원본 1,280행이 아예 안 들어왔다

`externalId` 가 붙으니 **"원본에는 있는데 우리 DB 에 없는 행"** 을 처음으로 셀 수 있었다.

| | 값 |
|---|---|
| sumaek 원본 | 6,151 |
| `externalId` 로 붙은 행 | 4,629 |
| 미상 233행이 걸친 후보 | 242 |
| **아예 없는 행** | **1,280** |

그 1,280행을 적재 파이프라인에 다시 태워 이유를 물었다 — **전량이 「단원 미분류」**다.
그림으로 제외된 것 0, 본문이 비거나 길어 잘린 것 0, 통과했는데 없는 것 0.

**그리고 전량이 「학년 미해석」이다 — §증상 1의 오배정 1,364행과 같은 뿌리다.**
확인 실험(다른 건 그대로 두고 학년 힌트만 교재명에서 뽑아 다시 태움):

| | 통과(ok) | 단원 미분류 |
|---|---|---|
| 지금 | 0 | 1,280 |
| 학년 힌트만 고치면 | **401** | 879 |

**결함 하나가 증상 둘을 만들고 있다** — 들어온 행은 틀린 학년 단원에 실리고(1,364),
안 들어온 행은 단원을 못 찾아 통째로 빠진다(1,280 중 최소 401).
남는 879행은 힌트 이름이 트리에 없는 것들이라(「기본 도형과 위치 관계」·「원의 현과 접선」
·「분산과 표준편차」·「가감법」) 별칭 판단이 따로 필요하다. 「틀린 매핑보다 미분류가 낫다」
원칙대로 원장님 확인 없이 붙이면 안 된다.

⚠️ **이 분석을 재현할 때 주의** — `extract-rpm.ts` 의 `RPM_SELECT` 는
`question_alignments → canonical_concepts` 를 조인해 `concepts` 를 넘긴다.
그걸 빼고 재현하면 단원 힌트가 비어 **"미분류 상위 힌트가 (빈 힌트) 713"** 이라는
엉뚱한 결론이 나온다. 실제로 1차에 그렇게 틀렸고, 원본 질의를 대조해 잡았다.
보고서 생성기는 이제 같은 재료를 쓴다.

## 3. C-3 회귀 검사 — 끝에서 끝까지 보는 검사 둘을 더 넣었다

기존 검사는 변환기 계약(원본 → 변환 직후)과 적재 상태 일부만 봤다. **변환은 잘 됐는데
그 뒤에 흘리는** 경우가 지난 4,862건 유실의 실제 모양이라, 원본과 적재본을 직접 잇는
검사를 더했다.

| 검사 | 방식 | 현재 |
|---|---|---|
| 원본에 정답이 있는 문항은 적재된 행에도 정답이 있다 | 기준선 | 4,534/4,552 **99.60%** |
| 원본 행이 `externalId` 로 우리 DB 에 닿아 있다 | 기준선 | 4,629/6,151 **75.26%** |

`db-answer-linked` 가 100%가 아닌 것은 **정상이고 고치면 안 된다.**
`recover-rpm-answers` 는 보기가 실제로 렌더되지 않는 문항에 번호 정답을 넣지 않는다
(시험지에 ①~⑤ 가 없는데 답만 "③" 이면 학생이 대조할 대상이 없다). 그렇게 일부러
보류한 행이 지금 18건이고, 그 수가 그대로 이 검사의 미달분이다. 코드 주석에도 적었다.

`db-source-coverage` 는 재이관이 조용히 행을 잃으면 떨어진다 — §2의 1,280행 같은 일이
다시 커지면 여기서 빨강이 된다.

결함 되돌리기도 하나 늘려 **6종**이 됐다. 전부 빨강 확인:

```
[choice-id]         → 잡음 (answer-filled, answer-marker-form)
[marker-drop]       → 잡음 (choice-marker-alive)
[answer-flatten]    → 잡음 (answer-filled, answer-marker-form)
[figure-blind]      → 잡음 (db-figure-linked)
[answer-blind]      → 잡음 (db-answer-linked)     ← 이번에 추가
[external-id-blind] → 잡음 (db-external-id)
결함 되돌리기 전부 빨강 — 검사가 살아 있다.
```

# C-1 2차 적용 — 해설 확정 214행 (2026-08-16, 원장님 승인)

## 1. 적용 전 보고 (조건 1)

> **`Problem.external_id` 컬럼에, `source='transformed'` 이면서 지금 NULL 인 214행을,
> sumaek `questions.id` UUID 값으로 채운다. 다른 컬럼·다른 source 는 건드리지 않는다.**

- 대상 선정 근거: 본문으로는 후보가 둘 이상이라 1차에서 미상으로 남긴 233행 중,
  **해설(`explanation`)이 원본 한 행에만 정확히 대응하고 그 대응이 단사(injective)인** 214행.

## 2. 되돌리는 법 (조건 2) — **이 214행에만 한정**

1차 4,629행과 섞이면 못 되돌리므로, 적용 대상 목록을 저장소에 **커밋해 두었다**:

```
scripts/qa/rpm-external-id-solution-basis.json     ← 214쌍 {problemId, externalId}
```

되돌릴 때는 그 파일의 `problemId` 에만 건다. 전체 `source='transformed'` 에 걸면
1차 4,629행까지 날아간다 — **절대 그렇게 하지 말 것.**

```sql
-- 되돌리기: 이 214행만 NULL 로. problem_id 목록은 위 JSON 의 pairs[].problemId.
UPDATE problem
   SET external_id = NULL
 WHERE source = 'transformed'
   AND id IN ( … pairs[].problemId 214개 … );
```

같은 일을 스크립트로 하려면 (Node, 드라이런 기본):

```bash
node -e '
const fs=require("fs");const {PrismaClient}=require("@prisma/client");
const {pairs}=JSON.parse(fs.readFileSync("scripts/qa/rpm-external-id-solution-basis.json","utf8"));
(async()=>{const p=new PrismaClient();
 const n=await p.problem.count({where:{source:"transformed",id:{in:pairs.map(x=>x.problemId)},NOT:{externalId:null}}});
 console.log("되돌릴 행",n);
 if(process.env.ALLOW_SHARED_IMPORT==="1"&&process.argv.includes("--apply")){
   const r=await p.problem.updateMany({where:{source:"transformed",id:{in:pairs.map(x=>x.problemId)}},data:{externalId:null}});
   console.log("되돌림",r.count);}
 await p.$disconnect();})();'
```

되돌린 뒤 `externalId` 합계는 **4,843 → 4,629** 로 돌아와야 한다.
