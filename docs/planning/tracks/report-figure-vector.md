## 2. 비용 ② — 시간 (10편 실측 × 외삽)

`map_exam()` 을 **PDF 원본이 있는 편에서 무작위 10편**(seed 11) 뽑아 실제로 돌렸다.

```
10편 5.2s · 편당 평균 0.52s (0.3 ~ 1.0s)
```

**외삽 — 1,902편 × 0.52s/편 = 989s ≈ 16.5분** (근거: 위 10편 실측 × 1,902/10).
⚠️ 이것은 **rect 를 구하는 시간**이지, 다시 오려내 저장하는 시간이 아니다.
300dpi 재크롭 비용은 별도로 재야 한다(아직 안 쟀다).

### 덤 — 매핑이 옛 파일과 같은지 **바이트로 확인했다**

「지금 `map_exam()` 이 주는 rect 가 그때 그 파일의 rect 인가」는 가정이면 안 된다.
네이티브 추출분은 `doc.extract_image(xref)` 의 바이트와 디스크 파일의 md5 를 견줄 수
있다(2026-08-18 「순서는 가정이 아니라 문항마다 확인되는 사실」).

10편 표본: 네이티브 66장 **66장 전부 md5 일치 (100%)** · 불일치 0.
→ 이 갈래는 원장의 `rect` 가 그 파일의 rect 임이 **파일마다 증명된다.**
클립 렌더분 12장은 바이트 대조가 안 된다(렌더는 재현이 아니다) — 픽셀 치수로 검산한다.

## 3. 비용 ③ — 네이티브 추출 vs 200dpi 클립 렌더 **(전량 실측)**

§15 가 「`extract-all-figures.py` 가 세기만 하고 안 찍는다」고 한 값이다.
표본이 아니라 **전 편(1,896편)을 다시 매핑해서** 셌다.

| | 장수 | 기출 `qNN` 12,925 중 |
| --- | ---: | ---: |
| **네이티브** (`xref` 로 원본 이미지를 그대로 꺼냄) | **10,779** | 83.4% |
| **클립 렌더 폴백** (200dpi 로 그 영역을 그림) | **2,059** | 15.9% |
| 대응 없음(아래 §5) | 87 | 0.7% |

⚠️ **네이티브 10,779장은 다시 잘라도 화질이 안 는다** — 이미 원본 비트맵 그대로다.
300dpi 재크롭으로 실제 이득이 나는 것은 **클립 렌더 2,059장 + RPM 1,718장**이다.
(브리프 지시대로 확장자로 나누지 않았다. `extract-all-figures.py` 의 `xref` 유무로
갈랐다 — 그게 두 갈래를 만드는 바로 그 분기다.)

### 그리고 **PNG 안에 렌더 해상도가 적혀 있었다**

PyMuPDF 는 `get_pixmap(dpi=D)` 로 그린 PNG 의 `pHYs` 에 D 를 적는다. 되읽으면
`199.9996`·`299.9994` 처럼 딱 떨어지지 않는 값이 나와서, **그 자체가 「우리가 클립
렌더한 것」이라는 지문**이다(원본 이미지를 그대로 꺼낸 PNG 는 `96.012` 처럼 그
이미지 자신의 값이고, JPEG 는 값이 아예 없다).

- 기출 클립 렌더 2,017장: `map_exam` 이 준 rect ↔ 파일에 적힌 dpi 가 **서로 검산**된다.
- **RPM 은 200dpi 만이 아니었다** — 1,239장이 **300dpi**, 479장이 200dpi 다.
  `DEFAULT_DPI = 200` 만 믿고 쟀으면 1,239장의 크기를 전부 1.5배로 잘못 적었을 것이다.
  (처음에 실제로 그렇게 재서 「27%만 맞는다」는 결과가 나왔고, 안 맞는 것들의
  가로세로비가 **정확히 1.5배**여서 드러났다.)

## 5. ㉯ 벡터 → SVG

### 5.1 거꾸로 간 것 셋 — 전부 실측으로 잡았다

**⑴ 글자를 다시 조판하면 안 된다.** 처음엔 `get_drawings()` 로 획을 옮기고 글자는
`<text>` 로 다시 썼다. 도형은 잘 나왔는데 **글자가 통째로 틀렸다**:

| 원본 | 다시 조판한 결과 |
| --- | --- |
| `℃` | `¾` |
| `1/2` · `-1/3` (분수) | 엉뚱한 낱글자 |
| `3²` | `3U` |

RPM 은 `EHsang`·`EHboNA` 같은 **자체 인코딩 수식 글꼴**이라 텍스트 레이어의
코드포인트가 뜻과 다르다. 기출은 `HyhwpEQ` 가 PUA(``)를 쓴다 — **표본 60건 중
58건**이 그렇다.

🔴 **그리고 이 오류는 겹쳐 대조에 안 걸린다.** `℃` 와 `¾` 는 픽셀 차이가 작아서
평균 절대차 **0.027 로 통과**했다. 「틀린 숫자는 아무 말도 안 한다」(CLAUDE.md
2026-08-19)와 같은 자리다. 그래서 글리프는 `text_as_path=True` 로 **윤곽선 그대로**
옮긴다.

**⑵ MuPDF 는 자기가 낸 SVG 를 자기가 못 읽는다.** `get_svg_image()` 산출물을 다시
열어 그리면 **온통 검다**(픽셀 극값 (0,0)). 그걸로 대조하면 전량이 「어긋났다」가
되고, 반대로 문턱을 낮추면 **아무것도 안 걸린다** — 판정자가 눈이 먼 채로 초록을
찍는 자리다. 그래서 **지면과 같은 렌더러(헤드리스 Chromium)** 로 그려 대조한다.
헤드리스라 원장님 화면 포커스를 안 뺏는다(절대 규칙 9).

**⑶ 온통 검던 진짜 원인은 쪽 배경 PNG 였다.** RPM 은 쪽마다 704×1123 배경 이미지를
까는데 그게 **거의 전부 0(검정)** 이다. 칸을 덮는 이미지는 ㉮ 원장의 `kind` 판정이
이미 「배경」으로 가르고 있었으므로 **같은 기준**으로 여기서도 뺀다.
덤으로 원본 크롭에 있던 **대각선 워터마크가 사라진다**.

### 5.2 쪽 SVG 를 솎는다

브리프 §2 가 경고한 대로 `get_svg_image()` 는 칸으로 잘라도 **쪽 전체**를 적고
`clipPath` 로 가릴 뿐이다(실측 443KB · path 414 · use 954).
`scripts/figure/svg_prune.py` 가 요소마다 bbox 를 계산해 칸 밖을 쳐낸다 —
`d` 는 명령을 제대로 훑는다(숫자만 짝지어 읽으면 `H`/`V` 에서 x·y 가 뒤바뀐다).
**애매하면 남긴다**(bbox 를 넉넉히 잡는다) — 잘못 지운 획은 지면에서 티가 안 난다.

실측: 443KB → **32KB** (92% 감소).

### 5.3 크기와 선 굵기 (§9)

- 인쇄 폭 = `min(70mm, rect 폭(pt)/72*25.4)` — ㉮ 원장이 준다.
  SVG 파일이 `width="…mm"` 로 **스스로 물리 크기를 들고 다닌다**(§14).
- 선 굵기는 **엔진 정본에서 읽어 온다**(`vendor/figure-engine/core/figure_svg.py`
  의 `stroke-width` 리터럴 — 못 읽으면 멈춘다). 실선 1.4 / 보조선 1.0 을
  **mm 로 환산**해 넣어 그림마다 물리 굵기가 같아지게 한다.
- ⚠️ **흰 선은 안 건드린다.** 배경 위에 칸을 나누려고 덧그린 «지우개»라 굵히면
  옆 칸 내용을 지운다(표 그림의 칸 구분선이 전부 흰 선이다).

🔴 **못 한 것 — 글자 크기는 `type_scale` 로 통일하지 못한다**(화질 브리프 §11 ⑥).
글리프가 윤곽선이라 크기를 바꾸려면 다시 조판해야 하고, 다시 조판하면 §5.1 ⑴ 의
틀린 글자가 돌아온다. **내용의 정확성을 택했다.** 선 굵기는 정규화한다 —
그건 내용을 안 바꾼다.

### 5.4 가드를 망가뜨려 봤다

## 6. 비용 ④ — **못 잰 것 · 못 한 것** (가장 중요한 항목)

### 6.1 못 잰 것

1. **300dpi 재크롭의 시간과 디스크 용량.** 이 트랙이 잰 20~28분은 **rect 를 구하는**
   시간이지 다시 잘라 저장하는 시간이 아니다. 화질 브리프 §6 이 요구한
   「600dpi 전량 재크롭 용량」도 **안 쟀다.**
2. **HWP 계열 1,444장의 원본 지면 크기.** HWPX `<hp:pic>` 의 HWPUNIT 크기 속성으로
   구할 수 있을지 **조사만 적어 두고 재지 못했다.**
3. **바이트 불일치 123건이 「다른 그림」인지 「같은 그림의 다른 인코딩」인지** —
   표본 12건만 열어 봤다(아래 6.3). 전량은 안 봤다.
4. **RPM 자리 못 찾은 600건의 진짜 자리.** 이 컴퓨터에 그때 계획이 없어 못 구했다.
   sumaek 원본에 다시 접속해 계획을 새로 만들면 되는지 **재 보지 않았다.**
5. **인쇄 지면에서 실제로 어떻게 보이는지.** 이 트랙은 `printOverflow.ts` 를 안
   건드렸다(다른 세션 작업 중). 그래서 **실물 검수는 못 했다** — 절대 규칙 6 대상이다.

### 6.2 못 한 것

1. **글자 크기 통일**(`type_scale`) — §5.3 참조. 윤곽선이라 못 한다. 하려면 다시
   조판해야 하고, 다시 조판하면 틀린 글자가 돌아온다.
2. **`hwppdf-qNN` 15장의 출처** — 어느 스크립트가 만들었는지 못 짚었다.
3. **SVG 를 지면에 물리는 일** — 새 디렉터리(`public/figures-svg/`)에 만들어 두기만
   했다. 바꿔치기는 §14(인쇄가 픽셀이 아니라 mm 를 보게 하는 일)와 함께 가야 한다.

### 6.3 「바이트가 다르다 123건」을 표본 12건 열어 봤다

`extract_image` 로 다시 꺼낸 바이트와 디스크 파일을 **픽셀로** 견줬다:

| | 건수 | 뜻 |
| --- | ---: | --- |
| 크기부터 다르다 | 5 | 그 자리에 **다른 그림**이 있다 |
| 픽셀 차이 0.2~0.85% | 7 | 같은 그림인데 **JPEG 재인코딩**된 것으로 보인다 |

그리고 별도로, 불일치·대응없음 252건에서 40건을 뽑아 **그 PDF 전체 이미지의 md5** 를
훑었더니 **38건은 원본 어디에도 없었다.** 즉 지금 N드라이브에 있는 PDF 는 그때 오려낼
때 쓴 `db/pages/<eid>/src.pdf` **캐시와 다른 파일**이다(그 캐시는 이 컴퓨터에 없다).
바이트가 맞는 10,656건은 두 파일이 그 이미지에 대해서는 같다는 뜻이다.

⚠️ 「픽셀이 거의 같으니 rect 를 인정하자」는 **안 했다.** 0.85% 차이가 재인코딩인지
다른 그림인지 12건으로는 못 가르고, 이 저장소의 규칙대로 **판정은 버리는 쪽**으로
둔다. 회수 상한은 123건 중 약 70건(0.5%)이다.

## 7. §14 — 인쇄 쪽에 무엇을 넘기나 (이 트랙은 **정하기만** 한다)

인쇄 코드(`src/lib/printOverflow.ts`)는 **다른 세션이 고치는 중**이라 안 건드렸다.
넘길 것만 정해 둔다.

- **어디에 두나 → 별도 대장.** `scripts/qa/reports/figure-rect-ledger.json` 의
  `figure` 키가 `public/figures` 기준 상대 경로이고, DB `figure_urls` 는
  `/figures/...` 를 담는다. 앞에 `/figures/` 만 붙이면 **바로 조회된다.**
  파일 이름에 mm 를 박는 방법은 경로가 바뀌어 DB 갱신이 따라와야 하므로 안 쓴다.
- **무엇을 넘기나** — `width_mm` · `height_mm`. 인쇄 폭은
  `min(70, width_mm)` 이다(§9).
- **SVG 는 스스로 들고 다닌다** — `width="…mm" height="…mm"` 로 나간다.
- **덮이는 범위** — 14,391 / 16,119 (89.3%). 나머지 1,728장은 mm 를 모르므로
  지금 규칙(픽셀 → 70mm 상한)을 그대로 둘 수밖에 없다. 그 사실을 **세어서** 넘긴다.
