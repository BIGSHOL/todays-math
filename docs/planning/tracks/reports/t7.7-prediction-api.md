1차에서 스키마 공백 때문에 `params` JSON 에 실어 뒀던 **소유자·위험 표시를 컬럼으로
옮기고**, 그 대가로 못 붙였던 **페이지네이션을 붙였다.** 병합 직후 저장 API 가 내던
500 18건(엔진 v0.5 파라미터 표류)도 함께 닫았다.

| | 상태 |
|---|---|
| `params.ownerUserId` → `PredictionRun.userId` 컬럼 | ✅ 제거 완료 |

## 1. 무엇을 만들었나 (누적)

`predictBlueprint`(엔진)로 예측을 만들어 `PredictionRun` 한 행으로 남기고,
그 기록을 읽는 API 3개를 붙였다.

| 파일 | 내용 |
|---|---|
| `src/contracts/predictionRun.contract.ts` | API 표면 계약 |
| `src/lib/predictor/predictionRunService.ts` | 근거 수집 · 누출 검사 · 저장 · 직렬화 · 소유권 |
| `src/app/api/predictions/route.ts` | `POST`(실행·저장) · `GET`(회차 목록) |
| `src/app/api/predictions/[id]/route.ts` | `GET`(회차 상세) |
| `src/__tests__/api/predictions.test.ts` | 32개 |
| `src/__tests__/helpers/predictionRunTestDb.ts` | T7.7 전용 인메모리 Prisma 대역 |

2차에서 추가로 손댄 남의 파일 2개 — **둘 다 코디네이터가 명시 허가한 범위다.**
- `src/contracts/predictor.contract.ts` — `predictorParamsSchema` 단일 정의를 여기 둔다.
- `src/lib/predictor/predictBlueprint.ts` · `scripts/predictor/backtest.ts` — 엔진 버전 상수.

`prisma/schema.prisma` 와 `prisma/migrations/**` 는 **여전히 한 줄도 건드리지 않았다.**

### 엔드포인트

- `POST /api/predictions`
  `{ series, targetPeriod, cutoffPeriod?, inputExamIds?, examDate?, params? }` → 201 + run 상세
- `GET /api/predictions/{id}` — 상세. 남의 run 은 403, 없으면 404.
- `GET /api/predictions?school=..&grade=..[&level=..&subject=..&page=..&pageSize=..]`
  → `{ data, meta: { page, pageSize, total } }`

### 신규 테스트 4건이 잡는 것

- 소유자·위험 표시·시행일이 **컬럼**에 쓰인다(`row.userId` · `row.riskFlags` · `row.examDate`).
- `params` 에 `ownerUserId`/`riskFlags` 가 **다시 들어오지 않는다** — 임시방편 회귀 방지.
  되돌아오면 목록 필터가 메모리로 내려가 페이지네이션이 틀어지기 때문에 여기서 막는다.
- 시행일을 안 주면 NULL 이다(대상 시점으로 날짜를 만들어 채우지 않는다).
- 페이지네이션이 **소유자 기준으로** 정확하다 — 남의 run 4+1건을 섞어 두고
  `total=4`, 페이지 간 id 중복 0 을 확인한다.

## 3. 판단이 필요했던 자리

### A. 코디네이터가 "이미 했다"고 한 것 중 둘이 저장소에 없었다

지시받은 시점에 `git merge origin/main` 이 가져온 것은 엔진 v0.5 뿐이었다.
`origin/main` · `origin/BIGSHOL/handoff-a-index` · `origin/phase/figures` 를 전부 뒤졌지만
마이그레이션 `20260816160000_prediction_run_owner_and_interval` 도, `predictor.contract.ts`
로 옮겼다는 `predictorParamsSchema` 도 없었다.

- **파라미터 단일화**는 내가 했다(엔진 v0.5 와 어긋나 저장 API 가 실제로 500 을 내고 있었다).
  지시하신 설계 그대로 — 정의는 `predictor.contract.ts` 하나, `predictionRun.contract.ts` 는
  재수출, 엔진에 양방향 `extends` 단언.
- **마이그레이션**은 손대지 않고 **물어봤다.** 공유 DB 에 이미 적용된 이름으로 파일을 새로
  쓰면 체크섬이 달라 다른 세션 전부가 migrate 드리프트를 본다. 원장님이 push 하셨고
  그 뒤 이어받았다.

### B. 병합 충돌 10곳 — 같은 일을 양쪽이 했다

`predictorParamsSchema` 를 main 과 내가 **동시에** `predictor.contract.ts` 로 옮겨
정의가 두 벌이 됐다(`TS2451 Cannot redeclare`). main 의 위치·섹션 배너를 남기고
필드 주석만 합쳤다. `sameRoundBoost` 상한만 10 → 20 으로 넓혔다 —
v0.5 에서 2→4 로 올랐고 다음 조정 여지를 막지 않기 위해서다.

`engineVersion` 은 내 쪽(`PREDICTOR_ENGINE_VERSION`)을 남기고 main 의
`PREDICTION_ENGINE_VERSION = "0.2.0"` 을 흡수했다. 나머지는 main 의 prettier 정렬을 따랐다.

### C. `params` 에 남긴 것 — 이건 임시방편이 아니다

`params` 에는 `predictor`(엔진 파라미터) · `evidence`(근거 집계) · `unavailableReason`
(청사진을 못 만든 이유)만 남았다. 셋 다 **"이 run 을 그대로 다시 돌리려면 무엇이
필요한가 / 왜 이런 결과가 나왔나"** 로, 컬럼이 아니라 실행 스냅샷에 속한다.
`unavailableReason` 만 성격이 애매한데(진단 문구), 컬럼을 하나 더 파기보다
스냅샷에 두는 편이 맞다고 봤다. **다르게 보시면 알려 주십시오.**

### D. `riskFlags` 컬럼은 `String[]` 이라 DB 가 값을 검사하지 않는다

계약 열거값으로 좁히되 모르는 값이 들어 있으면 **조용히 버리지 않고 던진다**
(`riskFlagsOf`). 필터링하면 화면에서 위험 표시가 소리 없이 사라진다.

## 4. 아직 남은 것 (T7.7 밖)

### `predictedScores` 는 여전히 빈 배열이다 — 지어내지 않았다

학생 개인 예상 점수를 내려면 능력 추정(11 §3 L3)과 난이도→점수 환산 계수(§2.7-3)가
필요한데 **둘 다 아직 없다.** 빈 배열을 저장하고 `학생응답_부족` 을 남긴다.

**T7.10 에 영향이 있다**: `ActualExamScore.predictedScore` 에 붙일 예측값이 아직 없다.
T7.11(환산 계수)이 나오기 전까지 T7.10 은 청사진 잔차만 다룰 수 있다.
(이번 마이그레이션에 들어온 `predicted_lower/upper/coverage` 도 채울 값이 없다.)

### `학교표기_불일치` riskFlag 는 여전히 붙이지 않는다

"자기 학교 과거가 0편"인 상황이 학교명 표기 불일치 때문인지 정말 자료가 없는 것인지
지금 데이터로는 가를 수 없다. T7.5(학교명 정규화) 결과와 대조하면 판정할 수 있을
것으로 **본다 — 아직 확인 못 한 추측이다.**

### 조회 부하 (측정하지 않은 전망)

자동 근거 수집은 코호트를 `(급, 학년, 과목)` 전체에서 문항까지 통째로 읽는다.
코퍼스 2,020편 규모에서는 문제없지만, 편수가 크게 늘면 연도 상한
(`year: { lte: cutoff.year }`) 같은 DB 단 필터가 필요하다. 같은 결과를 내는
최적화라 검증 대상만 늘어서 지금은 넣지 않았다. **실측하지 않은 전망이다.**
