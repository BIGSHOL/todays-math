## 0. 먼저 — 저장소와 공유 DB가 어긋나 있었다 (코디네이터 확인 요망)

후속 지시는 "네 브랜치는 이미 main 에 병합됐고, 마이그레이션
`20260816160000_prediction_run_owner_and_interval` 도 공유 DB 배포까지 끝났다"를 전제했다.
착수 전에 대조한 결과는 이렇다. **전부 명령 출력으로 확인한 사실이다.**

| 확인한 것 | 결과 |
|---|---|
| `4cf69af`(T7.10/T7.11)가 `origin/main` 에 있나 | **없다.** `git merge-base --is-ancestor` → false. `origin/main` = `f37e3d99` |
| `origin/main` 에 `src/app/api/predictions/**` 가 있나 | **없다.** 트랙 E 예측 API 는 아직 main 에 없다 |
| 마이그레이션 파일이 저장소에 있나 | **없다.** 로컬 20개 ref · 원격 4개 ref · 워크트리 13곳 전수 검색 결과 0건 |
| 그 마이그레이션이 **공유 DB** 에는 있나 | **있다.** `_prisma_migrations` 에 `20260816160000_prediction_run_owner_and_interval` 기록 확인 |
| 컬럼이 공유 DB 에 있나 | **있다.** `predicted_lower/upper/coverage` = `double precision` 널 허용, `prediction_run.user_id` = `uuid` NOT NULL |

즉 **DDL 은 공유 DB 에 배포됐는데 마이그레이션 파일과 스키마 변경이 저장소에 들어오지 않았다.**
이 상태로 두면 어느 세션이든 `prisma migrate dev` 를 돌리는 순간 drift 로 잡히고
**배포된 컬럼을 DROP 하자고 제안한다.**

원장님 판단으로 **내가 마이그레이션을 재구성해 넣었다**(아래 §1).

### 여기서 하나 더 나왔다 — 배포된 컬럼이 둘 더 있었다

공유 DB 를 스키마와 대조(`prisma migrate diff --from-url`)하니 지시받은 4개 말고
`prediction_run.exam_date`(DATE, 널 허용) · `prediction_run.risk_flags`(TEXT[], 널 허용)도
배포돼 있는데 스키마에 없었다. 값을 쓰는 쪽은 **T7.7**(예측 실행)이다
— T7.7 도 자기 서비스 머리말에 "riskFlag 컬럼이 없어 `params` JSON 에 싣는다"고 적어 두었다.

**남의 트랙 컬럼이지만 스키마에 선언만 해 두었다.** 선언하지 않으면 `prisma migrate` 가
매번 DROP 을 제안하기 때문이다. 이 트랙은 두 컬럼을 **읽지도 쓰지도 않는다.**

## 1. 마이그레이션 재구성 — `20260816160000_prediction_run_owner_and_interval`

배포된 DB 를 읽어 같은 상태를 내는 DDL 을 다시 만들었다. 추가한 것:

```
prediction_run     : user_id UUID NOT NULL (+ FK → user, + index [user_id, created_at DESC])
                     exam_date DATE, risk_flags TEXT[]        ← T7.7 소유, 선언만
actual_exam_score  : predicted_lower / predicted_upper / predicted_coverage  (DOUBLE PRECISION, 널 허용)
```

검증한 것과 못 한 것을 갈라 적는다.

- ✅ `prisma validate` 통과, `prisma generate` 통과.
- ✅ DDL 은 손으로 쓰지 않고 `prisma migrate diff`(스키마↔스키마) 산출을 그대로 썼다.
- ✅ **공유 DB 와 컬럼 단위 일치 확인** — `information_schema` 조회로 대조했다.
  `prediction_run` 23개 · `actual_exam_score` 12개가 스키마 선언과 정확히 같다.
- ✅ 인덱스·FK 는 첫 `migrate diff --from-url` 출력이 `exam_date`/`risk_flags` 두 줄뿐이었다는
  사실로 확인된다(그 외에는 차이가 없었다는 뜻).
- ❌ **두 컬럼을 넣은 뒤 `migrate diff --from-url` 을 다시 돌리려다 두 번 다 타임아웃했다**
  (Supabase 풀러). 컬럼 단위 대조로 갈음했다. **코디네이터가 한 번 더 돌려 drift 0 을 확인할 것.**
- ❌ 로컬 DB 전수 적용은 못 했다. 이 워크트리에 `.env` 가 없고 Docker 도 떠 있지 않다.

🔴 **공유 DB 에는 이 마이그레이션을 다시 실행하지 말 것.** 이미 적용돼 있다.
`prisma migrate resolve --applied 20260816160000_prediction_run_owner_and_interval` 로 표시한다.
(`prediction_run` 0행 · `actual_exam_score` 0행이라 `user_id NOT NULL` 자체는 안전했다.)

## 2. 작업 1 — 구간도 스냅샷으로 남긴다

T7.10 이 남겨 둔 어긋남(점수는 스냅샷을 지키는데 `intervalHit` 만 run 의 *현재* Json 으로
다시 판정되던 것)을 닫았다.

- 처음 저장할 때 `predictedLower` `predictedUpper` `predictedCoverage` 를 함께 복사한다.
- **재저장(점수 정정) 때는 덮어쓰지 않는다** — `predictedScore` 와 같은 규칙이다.
- `intervalHit` 은 **저장된 구간 스냅샷**으로 다시 센다. run 의 Json 을 보지 않는다.
  얼려 두지도 않는다 — 점수 정정은 *실제값*이 움직인 것이므로 다시 세는 것이 맞다.

### 구간이 없었을 때의 판단 (근거를 남기라 하신 부분)

`interval_hit` 은 NOT NULL 이라 무언가는 들어가야 한다. **`false` 를 넣되, 집계의
분모에서 뺀다.** 근거:

- 빗나감으로 세면 구간이 실제보다 **부정직해 보이고**, 적중으로 세면 **부풀려진다.**
  둘 다 없는 근거로 지표를 만드는 것이다.
- 그래서 "판정 가능 여부"를 값이 아니라 **구간 스냅샷의 존재**로 판별한다
  (`hasInterval = lower !== null && upper !== null`).
- 계약에 `intervalCount`(판정 가능 표본 수)를 따로 넣어 요약이 스스로 설명하게 했다 —
  "30명 중 판정 가능한 28명 기준 적중률"이 그대로 읽힌다.
- T7.11 도 같다. 판정 가능한 표본이 0이면 `intervalHitRate` 는 **null** 이고
  구간 정직성 판정도 하지 않는다.

회귀 테스트를 넣었다(지시한 짝):
- 저장 후 run 의 Json 구간을 65~79 → 40~60 으로 바꿔도 `intervalHit` 이 **안 움직인다.**
- 점수를 78 → 95 로 정정하면 **저장된 구간** 기준으로 다시 세어 적중 → 빗나감으로 바뀐다.
- 구간 없는 예측은 세 컬럼이 null 이고 `intervalCount` 분모에서 빠진다.

## 3. 작업 2 — 소유권 경계를 컬럼으로 옮겼다

이전 전제("회차는 공용, 학생 점수는 소유 원장만")를 **버렸다.** 이제 이중이다.

1. **회차** — `PredictionRun.userId` 가 로그인 원장이어야 한다. 저장·조회 **둘 다** 막는다.
   남의 회차면 403.
2. **학생** — `requireOwnedStudent` 는 그대로 유지했다(지시대로). 조회도
   `where: { student: { class: { userId } } }` 로 한 번 더 거른다.

`requireOwnedPredictionRun` 은 **T7.7 브랜치에만 있고 main 에 없다**(확인 완료).
그 헬퍼는 `params.ownerUserId`(JSON) 를 읽는 방식이라 컬럼이 생긴 지금은 어차피 바뀐다.
`predictionRunService.ts` 는 T7.7 소유라 손대지 않았고, 대신 이미 읽어 둔 회차의
`ownerUserId` 로 라우트에서 직접 비교한다. **T7.7 병합 뒤 그 헬퍼 하나로 합칠 것**(§6-3).

## 4. 작업 3 — `scripts/predictor/calibration-report.ts` (읽기 전용)

`estimateCalibration` 을 실제로 부르는 자리를 만들었다.

- `ActualExamScore` 를 run 과 함께 읽어 표본을 만들고, 단계별 채택·홀드아웃 MAE·
  학교별 축소 계수·편향·구간 적중률을 마크다운 표로 찍는다.
- **DB 에 쓰지 않는다.** `findMany` 하나뿐이라 `--apply`/`ALLOW_SHARED_IMPORT` 게이트가 없다
  (그 게이트는 *쓰기* 장치다). 대신 **어느 DB 를 읽었는지 항상 머리에 찍는다.**
- 구간 신뢰수준은 표본에서 **유도**한다. 값이 섞여 있으면 하나로 단정하지 않고
  정직성 판정을 건너뛴다.
- 화면 연결은 하지 않았다(T7.14 소유).

### 실제로 돌린 결과 — 공유 DB 대상, 읽기 전용

```
# 보정 계수 리포트 (T7.11)

- 읽은 DB: aws-0-ap-northeast-2.pooler.supabase.com — 공유 Supabase — 프로덕션이라 적재 안 함
- 실측 행 수: 0
- 구간 신뢰수준: (구간 스냅샷 없음)
- 이 스크립트는 DB 에 쓰지 않는다(읽기 전용).

## 판단 불가

- 사유: 표본_부족
- 표본: 0건 / 필요: 20건
- 실측 표본이 0건이다. 20건 미만에서는 계수를 추정하지 않는다.

실측이 아직 한 건도 없다. **이것이 정상 출력이다** — 표본이 없으면 계수를 지어내지 않는다.
```

지시대로 **여기서 멈췄다.** 숫자를 만들어 내지 않았다.
"0건이면 표를 그리지 않는다"를 테스트로도 못 박았다(`0.000` 이 출력에 없어야 한다는 단언 포함) —
표 틀이 이미 있으면 채우고 싶어지는 것이 이 실수의 재발 경로라서다.

## 6. 코디네이터가 확인해야 할 것

1. **🔴 `origin/main` 에 이 브랜치가 없다.** 후속 지시의 전제와 다르다. 병합이 실제로
   안 됐는지, 다른 원격을 보고 계신 건지 확인 필요. T7.7/T7.9/T7.14 브랜치도 전부 미병합이다.
2. **🔴 재구성한 마이그레이션을 공유 DB 에 다시 실행하지 말 것.**
   `prisma migrate resolve --applied` 로 표시하고, `migrate diff --from-url` 을 한 번 돌려
   drift 0 을 확인해 주시라(§1 에서 내가 못 끝낸 검증).
3. **T7.7 병합 뒤 소유권 검사를 한 곳으로 합칠 것.** 지금은 내 라우트가 `ownerUserId` 를
   직접 비교한다. `requireOwnedPredictionRun` 이 컬럼 기반으로 바뀌면 그것으로 대체.
   T7.7 이 `params.ownerUserId` 에 싣던 우회도 컬럼으로 옮기면 된다.
4. **`exam_date` · `risk_flags` 를 선언만 해 둔 것**(§0)이 T7.7 의도와 맞는지.
   타입은 배포된 DB 를 그대로 옮겼을 뿐 설계 판단을 한 것이 아니다.
5. **실측 잔차는 여전히 0건이다.** `MIN_CALIBRATION_SAMPLES = 20` 은 통계적 근거이지
   이 프로젝트 실측 근거가 아니다. 실제 잔차가 쌓이면 그 분포로 다시 정해야 한다.
   첫 실측 회차에서는 계수를 자동 적용하지 말고 원장님 눈으로 한 번 보시길 권한다.
6. **MSW 목 핸들러 · `prismaTestDouble` 모델은 여전히 추가하지 않았다.** 공유 파일이라
   T7.7·T7.14 와 충돌한다. API 테스트는 파일 단위 `vi.mock("@/lib/db")` 로 돌린다.
