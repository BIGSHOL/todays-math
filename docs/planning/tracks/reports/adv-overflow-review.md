## 2. 🔴 A — 문제지 자에 «세로로 쌓이는 수식» 항이 없다

**근거** `src/lib/printOverflow.ts:352` (지금은 있다) · 리뷰 전에는 `estimateSolutionPx`(`:600`) 에만 있었다
**재현** 옛 `_adv-overflow-impl.test.ts` [적대④-A] → 승격 `src/__tests__/unit/printGeometryPin.test.ts` [적대④-A]

보고서 §3 은 해설 자에 「세로로 자리를 더 먹는 수식」 항(+4px/개)을 넣으며 이렇게 적었다:

> 20px 넘게 **과소평가**하는 비율이 13.5% → 6.7% 로 준다. **과소평가는 곧 놓침이라
> 정확도보다 이쪽이 중요하다.**

그 문장이 옳다. 그런데 **같은 항이 문제지 자에는 없다.** 규칙은 맞는데 배선이 한쪽만 됐다.

### 확인 — 표본을 눈으로 봤다

보고서가 스스로 적은 「20px 넘게 과소 17.9%」(다시 재니 17.6% · 8,300건)를 부류로 갈랐다
(`scripts/qa/analyze-height-error.ts`, 새로 만든 도구):

```
세로 수식이 하나라도 있는 비율 — 과소 **97.3%** · 오차 20px 이내 32.3%

세로 수식 개수별 — 평균 오차          20px 넘게 과소
  0개    27,516건   +5.4px               0.8%
  1~2개   9,851건   −5.2px              14.5%
  3~5개   6,976건  −17.1px              63.3%
  6~10개  2,582건  −28.1px              79.6%
  11개~     227건  −37.5px              74.9%
```

**한 방향이다.** 세로 수식이 없으면 살짝 과대(안전)하고, 있으면 개수에 비례해 과소하다.
가장 크게 놓친 표본을 눈으로 보면 이유가 그대로 보인다 —
`9ce9d437` 는 보기 다섯이 전부 2행 `pmatrix` 인데, `displayWidth` 는 격자를 **한 줄로 이어**
폭으로 세므로 «높이»가 통째로 빠진다(실측 469px, 추정 273px).

### 고친 것

해설 자의 상수·정규식을 **그대로** 문제지 자에도 건다 — 두 자가 한 숫자를 쓴다.

```
문제지 47,152건   |오차|≤20px  71.0% → 82.7%    20px 넘게 과소  17.6% → 5.2%
                  놓침 109 → 25 (이어지는 장) · 100 → 19 (첫 장)
세로 수식 개수별 평균 오차  3~5개 −17.1px → −2.4px · 6~10개 −28.1px → −4.0px
```

값은 **4px 그대로** 뒀다. 6px 이면 놓침이 한 자릿수로 내려가지만 헛것이 그만큼 늘어
경고 부담이 커진다 — 그리고 4px 은 해설에서 이미 검증된 값이라
**한 숫자를 두 곳이 쓴다**는 성질이 더 값지다.

### 남은 것

놓침 25건(이어지는 장)·19건(첫 장)이 남는다. 대부분 **행렬 보기**다 —
`\begin{pmatrix}` 하나가 실제로는 2~3줄을 먹는데 +4px 로는 못 따라간다.
행 수만큼 더 세 보았으나(환경 시작을 따로 센 변형) 놓침이 3건 줄고 헛것이 11건 느는
**맞바꿈**이라 넣지 않았다. 근거를 남기니 다음 사람이 다시 재면 된다.

## 3. 🔴 B — 칸은 «몇째 장»이 아니라 «그 장에 몇 개»로 갈린다

**근거** `src/components/print/TestPrint.module.css` `.problemItem { flex: 1 }` · `src/lib/printGeometry.ts:39-40`

수리는 「판정이 **장**을 안다」를 큰 성과로 적었다(첫 장 19줄 / 이어지는 장 23줄).
그런데 `.problemItem` 은 `flex: 1 1 0%` 다 — 칸은 **그 장의 문항 수로 나뉜다.**

지면에서 직접 쟀다(`scripts/qa/measure-paper-units.tsx`, 이번에 측정 기능을 넣었다):

```
                 2문항일 때   1문항일 때
이어지는 장        484px       997px      ← 2.06배
첫 장              405px       838px      ← 2.07배
```

`packProblems` 는 장당 2문항으로 자르므로 **문항 수가 홀수면 마지막 장에 하나가 남는다.**

전수로 재면 그 자리의 경고는 이어지는 장과 같은 **8.00%** 였는데, 실측으로 997px 을
넘는 문항은 **0.32%** 뿐이다 — 즉 그 자리의 경고 중 **7.7%p 가 거짓**이었다.
지금은 1.93% 로 준다.

> 브리프의 「임계값을 물려받을 때 분모가 같은지부터 보라」가 정확히 이 자리다.

## 4. 🔴 C — 적재가 `figure_dims` 를 안 채운다 (수리가 오늘 자에만 유효했다)

판정은 그림 높이를 `problem.figure_dims` 에서만 읽는다. 그 컬럼은 backfill 스크립트가
**한 번** 채웠다(8,442건). 그런데 문항이 들어오는 길은 `figureUrls` 만 쓰고 있었다 —

즉 **2026-08-18 이후에 들어오는 그림 문항은 전부 «모른다»** 다. 얼마나 나쁜가:

### 고친 것

- **한 장이라도 못 읽으면 통째로 비운다.** 반쪽 배열은 판정이 어차피 «모른다»로 받는데,
  넣어 두면 «안다»고 착각할 여지만 남는다.
- `backfill-figure-dimensions.ts --check` 로 「그림은 있는데 치수가 빈 문항」을 센다.
  지금 **0건**.

## 5. 🟡 D — `--revert --apply` 가 공유 DB 쓰기 게이트를 건너뛴다

**근거** `scripts/qa/backfill-figure-dimensions.ts:86-92` (지금은 게이트가 먼저다)

`--apply` 는 `ALLOW_SHARED_IMPORT=1` 을 요구한다(D-31, 2026-08-14 적재 사고 뒤 굳은 규칙).
그런데 `--revert` 분기가 **그 검사보다 위**에 있었다:

```ts
const apply = process.argv.includes("--apply");
if (process.argv.includes("--revert")) return revert(apply);   // ← 여기서 나간다
if (apply && process.env.ALLOW_SHARED_IMPORT !== "1") throw …   // ← 여기까지 안 온다
```

`npx tsx scripts/qa/backfill-figure-dimensions.ts --revert --apply` 한 줄이 환경변수 없이
공유 DB 의 `figure_dims` **전량**을 지운다. 지워지는 것은 판정의 유일한 근거이고,
**에러 없이 숫자만** 나빠진다(재현율 99.1% → 65.8%). 되돌리기도 쓰기다.

멱등성·되돌리기 자체는 확인했다 — 재실행은 「쓸 것 0 · 이미 같음 8,442」이고,
짝이 어긋난 채 써지는 경로는 없다(모든 장을 읽어야만 쓴다).
다만 **`figure_urls` 가 나중에 바뀌면 `figure_dims` 가 조용히 낡는다** —
지금 그런 경로는 저장소에 없지만, 생기면 `--check` 가 잡는다(길이 짝만 보므로
«같은 장수, 다른 그림» 은 못 잡는다. 그건 적재가 같이 쓰게 해야 한다).

공유 DB(D-31)는 다른 트랙이 `apply-*` 로 본문을 고친다. 지문 대조를 붙이자마자 걸렸다:

### 고친 것

- `--json` 이 캐시 옆에 지문(`*.manifest.json`)을 남긴다 — 지면 원문 8개 파일 + KaTeX 버전 +

- 지문에 **문항별 지문**도 넣어 «바뀐 문항»은 표본이 아니라 **반드시** 다시 잰다.

  일이 생긴다 — 그건 확인이 아니라 요행이다.
- `--repair` — «다른 것»을 두 갈래로 가른다. **본문이 바뀐 문항**은 당연히 다르므로

> 이 리뷰의 최종 숫자를 내는 동안 **DB 가 두 번 더 바뀌었다.** 전수 재측정(30분)을
> 도는 사이에도 바뀐다 — 그래서 «다시 재라»만으로는 끝나지 않고, 바뀐 자리를 집어
> 깁는 길이 필요하다. 그게 `--repair` 다.

목록(지면 원문 8개)은 손으로 유지하므로 **샌다.** 그래서 지문에 실측 칸 높이와
문항 본문을 같이 넣었다 — 목록에서 빠진 파일이 지면을 바꿔도 칸이나 본문이 같이 움직이면

앞 트랙의 §7 ⑴⑵⑶ 은 그대로 유효하다. 여기에 둘을 더한다.

### ⑷ 출제가 「칸에 안 들어가는 문항」을 후순위로 돌린다

`SelectableProblem` 에 `content`·`figureUrls`·`figureDims` 를 실어 `selectProblems` 가
`assessOverflowRisk` 를 볼 수 있게 한다. **제외가 아니라 후순위** — 풀이 얇은 단원에서
출제가 막히면 안 된다(D-20·INSUFFICIENT_PROBLEMS).
25문항 기준 경고 기대 **2.12건 → 0에 가깝게**. 인쇄물이 달라지므로 확정 대상.

### ⑸ 큰 문항을 첫 장에 안 놓는다 (자리만 바꾼다)

첫 장 칸이 79px 좁아 넘침 비율이 12.65% 로 이어지는 장(5.81%)의 **2.2배**다.
문항을 바꾸지 않고 **순서만** 바꿔 큰 문항을 3번 이후로 보내면
경고 기대의 상당 부분(첫 장 몫 0.34건/장)이 사라진다. ⑷보다 훨씬 작은 변경이지만
**문항 자리가 바뀌므로** 역시 D-07 이다.

> ⑷·⑸ 중 하나만 해도 §G 의 「88%」가 크게 내려간다. 판정 쪽에서는 더 할 게 없다 —
> 정밀도를 100%로 만들어도 79%다.

### 곁가지 — 캐시가 스스로 어긋난 줄을 갖게 되는 길

`--verify` 의 표본 수가 **홀수**면 마지막 장이 한 문항이 되고, 그 칸은 997px 이라
캐시(484px)와 다른 것을 잰다 — 이 리뷰가 §B 에서 찾은 결함을 도구가 그대로 밟았다.
지금은 표본을 짝수로 **채워서**(버리지 않고) 맞추고, 그래도 캐시 안에 칸이 어긋난 줄이
있으면 `--verify` 가 **그 줄을 반드시 다시 잰다.** 버리는 쪽으로 맞추면 하필
「반드시 봐야 할 줄」이 빠진다 — 실제로 한 번 그랬다.

### 곁가지 — 탐침 HTML 이름이 하나라 측정 둘이 겹치면 남의 지면을 잰다

`paperProbe.writeProbe` 가 `probe-overflow.html` **한 이름**을 쓴다. 이 저장소는
오르카 다중 세션이 기본인데(절대 규칙 9), 측정 둘이 겹치면 서로 덮어쓴다.
실제로 겹쳐서 Windows 에서 `EBUSY` 로 두 번 죽었다 — **다른 OS 였다면
한쪽이 남의 지면을 재고도 조용히 성공했을 것이다.** 조용한 쪽이 훨씬 나쁘다.
이름에 프로세스 번호를 붙였다.

### 곁가지 — 측정 스크립트의 «요약»이 제 판정을 잘못 채점하고 있었다

`measure-print-overflow.tsx` 는 JSON(캐시)은 제대로 냈지만, 화면에 찍는 요약에서
`figure_dims` 를 **조회하지 않고** 판정을 돌렸다. 그래서 그 요약의 「놓침」은 늘
«치수를 전부 모를 때»의 값이었다 — 실제 제품 판정보다 훨씬 나빠 보인다.
같은 파일 안에서 «재는 쪽»과 «채점하는 쪽»이 다른 입력을 보고 있었다. 고쳤다.

## 13. 이번에 되풀이된 교훈

- **지표의 «참»이 제품 상수에서 나오면 그 지표는 아무것도 증명하지 못한다.**
  칸 상수를 망가뜨리니 재현율이 **올랐다**. 실측값이 캐시에 이미 있었는데 안 썼다.
  채점기가 제품 함수를 부르는 것(§E 의 일치 검산)과, 채점기가 제품 **상수**로
  정답을 정하는 것은 다른 일이다. 앞은 좋고 뒤는 동어반복이다.
- **가드는 «망가뜨려 봐야» 가드인 줄 안다.** 상수 29개를 하나씩 변이시키니 9개가
  초록이었다. 문서·리뷰로는 하나도 안 나왔다 — 여기서도 그랬다.
  그리고 초록이던 이유의 절반은 **기대값을 그 상수에서 만들어 썼기 때문**이다.
- **규칙이 옳아도 배선이 한쪽만 되면 그쪽 지표만 좋아진다.** 세로 수식 항이 해설에만
  걸려 있어서 해설 과소는 6.7% 인데 문제지 과소는 17.9% 였다. 같은 함수를 쓰는
  두 자가 있으면 **한 숫자를 두 곳이 쓰게** 해야 한다.
- **임계값의 분모를 볼 때 «칸이 하나인지»부터 보라.** 한계 23·19 의 유도는 옳았다.
  다만 칸이 넷이었다(484·405·997·838).
- **오늘 자 데이터의 성적을 «판정의 성적»으로 적지 말 것.** 치수를 채운 8,442건에서 99.2%,
  안 채운 문항에서 60.4%. 앞으로 들어올 문항이 어느 쪽인지 확인하지 않으면
  보고서의 숫자는 **오늘 하루짜리**다.
- **공유 DB 를 쓰는 캐시는 지면을 안 건드려도 낡는다.** 다른 트랙이 본문을 고친다.
  「그때 확인했다」는 것을 계속 참으로 유지하는 장치가 있어야 한다 —
  실제로 이 리뷰 도중에 한 행이 바뀌어 그 문항의 지면 높이가 234px 늘었다.
