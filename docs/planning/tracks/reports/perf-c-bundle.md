## 1. 잰 방법 (숫자를 믿기 전에 읽을 것)

Next 16 은 빌드 로그에 **라우트 크기를 더 이상 찍지 않는다.** 그래서 두 가지로 쟀다.

| 측정 | 대상 | 근거 파일 |
|------|------|-----------|
| A. 프리렌더 HTML 이 싣는 `/_next/static/*.js` 합계 | 정적(○) 라우트 | `.next/server/app/*.html` |
| B. 라우트별 first-load JS | **정적·동적 전부** | `.next/diagnostics/route-bundle-stats.json` (`next build --experimental-analyze`) |

A 와 B 는 정확히 **110KB** 차이 난다 — A 는 레거시 브라우저용 `nomodule` 폴리필
청크(110KB)를 포함하고 B 는 뺀다. 둘 다 맞는 숫자다. 아래 표에는 어느 쪽인지 적었다.

**앞으로는 B 를 정본으로 쓴다:**

```bash
npm run analyze          # 분석 빌드 + 라우트별 표
npm run bundle:report -- --baseline docs/planning/tracks/reports/bundle-baseline.json
```

기준선(`bundle-baseline.json`)은 이 작업 직후 값으로 넣어 뒀다. 0.5KB 넘게 커진
라우트는 `▲` 로 표시된다. **의도한 증가면 기준선을 갱신하고, 아니면 원인을 찾을 것.**

## 3. 안 한 일 ①: KaTeX CSS 를 수식 라우트로 옮기기 — **보류 (차단됨)**

`src/app/layout.tsx` 의 전역 `import "katex/dist/katex.min.css"` (53KB + `@font-face` 60개)가
수식이 없는 로그인·가입·메인·반관리·계기판까지 렌더 블로킹한다. 이건 사실이다.

**그런데 지금 떼면 안 된다.** layout.tsx 주석이 근거를 남겨 뒀다 —
「일부 라우트만 로드하면 MathML 이 이중으로 보인다」. 이 현상의 원인은 `rehype-katex`
가 기본값 `output: "htmlAndMathml"` 로 렌더하는 것이고, 해결은 `output: "html"` 적용
가능 여부를 **렌더 축 세션이 조사해 이 디렉터리에 메모를 남기는 것**으로 정해져 있었다.

**작업 당시(2026-08-17 18:20)에는 그 메모가 없었다** — 렌더 축 브랜치에만 있었고
아직 병합 전이라 이 워크트리에서 보이지 않았다.

> **[병합 시 갱신 — 오케스트레이터, 2026-08-17]**
> 메모는 나왔고 결론은 **"적용하지 않는다"** 다
> (`perf-b-rehype-katex-output.md`). 지면·화면은 문항 30건 전량에서 한 픽셀도
> 안 달라지지만, `output:"html"` 은 `.katex-mathml` 을 없앤다 — 화면에 보이는
> `.katex-html` 은 `aria-hidden="true"` 라, **보조기술이 수식을 읽는 유일한 통로가
> 사라진다.** DOM −31% 와 맞바꿀 것이 아니다.
>
> 따라서 아래 "다음 사람이 할 일"의 전제가 바뀌었다. CSS 이동은 **메모를 기다리는
> 상태가 아니라, 다른 길을 찾아야 하는 상태**다.

> ⚠️ **CSS 만 먼저 떼지 말 것.** CSS 없이 KaTeX 마크업만 나가면 수식이 깨져 보이고,
> MathML 이중 표시는 CSS 를 뗀 뒤에야 드러난다. 두 변경은 **한 세트**다.

**다음 사람이 할 일** (전제가 바뀌었으니 아래 순서로):

`output:"html"` 은 못 쓴다(위 갱신). 그러면 MathML 은 계속 나오므로, CSS 를 라우트로
옮기면 「MathML 이 이중으로 보인다」가 그대로 재현될 수 있다. 남은 길은 셋이다.

1. **먼저 재현부터 확인한다.** layout.tsx 주석의 그 현상이 지금 KaTeX·Next 버전에서도
   실제로 나는지 아무도 최근에 확인하지 않았다. 안 나면 CSS 이동만으로 끝난다.
2. 난다면, `.katex-mathml { display: none }` 만 담은 **아주 작은 전역 CSS**를 남기고
   나머지 53KB(글리프 폰트 60개 포함)를 수식 라우트로 옮긴다. MathML 은 DOM 에 남아
   보조기술이 계속 읽고, 이중 표시는 그 한 줄이 막는다.
3. 그래도 안 되면 현행 유지. 53KB 를 아끼려고 수식이 깨지거나 화면이 흔들리면 손해다.

어느 쪽이든 마지막은 네 화면 육안 확인이고 **인쇄는 실물 출력**이다(절대 규칙 6).
예상 이득: 수식 없는 6개 라우트에서 CSS 53KB.

## 4. 안 한 일 ②: 서버 페칭으로 폭포수 없애기 — **조사·제안만 (구현 금지 범위)**

### 4.1 현재 구조

모든 페이지가 **얇은 서버 껍데기**이고 데이터는 클라이언트가 마운트 후 다시 가져온다.

```
HTML(데이터 없음) → JS 다운로드/파싱 → hydration → fetch → 페인트
```

`/` 의 HTML 은 **7.5KB** 다 — 내용이 없다는 뜻이다. 그리고 fetch 가 한 겹이 아니다:

| 라우트 | 마운트 후 요청 | 파도 |
|--------|----------------|------|
| `/` | classes · tests · units · metrics → **그 다음** 반마다 progress | **2파** (N+1) |
| `/classes` | (units 는 서버) classes → 그 다음 students · progress | **2파** |
| `/tests/new` | classes · units → 그 다음 students | **2파** |
| `/problems` | problems · units | 1파 |
| `/tests/[id]` | tests/{id} | 1파 |
| `/exam`, `/exam/[id]` | rounds | 1파 |
| `/tests/[id]/print` | **없음 — 서버가 Prisma 로 직접 읽는다** | 0 ✅ |

`/` 가 가장 나쁘다. 반이 5개면 hydration 후 **4 + 5 = 9회** HTTP 왕복이고,
각 요청이 다시 `auth()` 세션 검증 + Prisma 질의를 반복한다.

### 4.2 이미 정답이 저장소 안에 있다

`src/app/(main)/tests/[id]/print/page.tsx` 는 서버 컴포넌트에서 `getSessionUser()` +
`db.test.findFirst()` 를 직접 호출하고 완성된 데이터를 클라이언트 컴포넌트에 props 로
내려준다. `/classes` 와 `/onboarding` 도 units 만은 그렇게 한다. **패턴을 새로
발명할 필요가 없다** — 이미 쓰는 방식을 나머지 라우트로 넓히는 일이다.

### 4.3 옮길 수 있는가 — 라우트별 판단

| 라우트 | 서버 페칭 가능? | 근거 |
|--------|------------------|------|
| `/` | **가능, 효과 최대** | 5개 API 가 전부 읽기 전용. `loadMainDashboard` 를 서버 함수로 옮기면 N+1 이 한 번의 Prisma 질의로 접힌다 |
| `/classes` | 가능 | 이미 units 는 서버. classes/students/progress 를 같은 자리에서 읽으면 됨 |
| `/tests/[id]` | 가능 | print 라우트와 사실상 같은 데이터 |
| `/problems` | **부분만** | 첫 페이지는 서버, 이후 필터·페이지 이동은 클라이언트로 남겨야 함 |
| `/tests/new` | 부분만 | 초기 목록은 서버, 반 선택에 따른 학생 조회는 클라이언트 |
| `/exam`, `/exam/[id]` | 가능 | 읽기 전용 조회 |

### 4.4 **D-07(화면 형태)이 바뀌는가 — 바뀐다. 그래서 원장님 확정이 먼저다.**

여기가 이 항목을 구현하지 않은 이유다. 성능만 보면 명백한 이득이지만 **보이는 것이 달라진다**:

1. **로딩 상태가 사라진다.** 지금은 「불러오는 중」 → 내용이다. 서버 페칭이면 내용이
   바로 온다. 더 좋아 보이지만 **화면의 상태 수가 줄어드는 형태 변경**이다.
   05-design-system 에 로딩 표현이 확정돼 있다면 그 항목이 무의미해진다.
2. **오류 표현이 달라진다.** 지금은 화면 안에 「목록을 불러오지 못했습니다」가 뜬다.
   서버에서 실패하면 error boundary / 빈 상태 등 **다른 자리**에 다른 모양으로 뜬다.
   이건 문구·위치·복구 동선이 모두 바뀌는 일이라 D-07 정면이다.
3. **입력 후 반응이 달라진다.** 진도 기록·반 추가·문제 등록은 지금 클라이언트 상태를
   직접 갱신해 즉시 반영된다. 서버 페칭으로 옮기면 `router.refresh()` 나 서버 액션 뒤
   재조회가 되어 **체감 반응 속도와 깜빡임**이 달라진다. 원장이 매일 쓰는 동작이다.

> **결론: 이 항목은 성능 작업이 아니라 화면 설계 변경이다.** 절대 규칙 1에 따라
> 원장님 확정 없이 착수 금지. 확정을 받으러 갈 때는 「로딩 상태를 없앨지」,
> 「실패했을 때 어디에 무엇을 띄울지」, 「저장 후 화면이 어떻게 갱신될지」
> 세 가지를 시안으로 들고 갈 것.

### 4.5 확정이 나면 권하는 순서

1. `/` — 이득이 가장 크고(2파 + N+1 제거) 참고할 구현(print)이 있다.
2. `/tests/[id]` — print 라우트와 데이터가 겹쳐 재사용이 쉽다.
3. `/classes` — 이미 절반이 서버다.
4. `/exam`, `/exam/[id]`.
5. `/problems`, `/tests/new` 는 **첫 페이지만** 서버로. 필터·페이지 이동을 서버로 옮기면

각 단계마다 `npm run analyze` 로 기준선을 갱신하고, HTML 크기가 실제로 커졌는지

## 5. 알아 둘 부작용 두 가지

### 5.1 `optimizePackageImports` 는 이 저장소에서 **효과가 0 이었다**

빈 배열 / 4개 목록 / 8개 목록(next-auth·katex·@prisma/client 포함) 셋 다
라우트별 first-load 와 static chunks 총량(1,482.6KB)이 **바이트 단위로 동일**했다.
Turbopack 이 이미 같은 일을 하는 것으로 보인다. 설정은 나중을 위한 방어선으로만
남겼고 주석에 실측 결과를 적어 뒀다. **번들이 줄어든 근거로 이 설정을 인용하지 말 것** —
실제로 줄인 것은 C-1(zod 지연)과 C-2(KaTeX 지연)다.

### 5.2 `@next/bundle-analyzer` 는 Turbopack 빌드에서 **아무것도 만들지 않는다**

패키지 소스가 직접 그렇게 말한다 — `process.env.TURBOPACK` 이면 경고만 찍고 빠진다.
그냥 붙였으면 **리포트가 없는데 빌드는 초록인 계측기**가 될 뻔했다. 그래서
`npm run analyze:webpack` (webpack 강제) 로만 쓰고, 정본 숫자는 Turbopack 네이티브
분석기(`npm run analyze`)로 잡았다. 둘 다 실제로 산출물이 나오는 것을 확인했다.

### 5.3 테스트 2건을 고쳤다 — 둘 다 **단언이 아니라 대기 방식**

- `ProblemBank.test.tsx`: 등록 폼 단언에서 `getByRole` → `await findByRole`.
  패널이 실제로 비동기가 됐으니 대기를 붙인 것이고 검증 내용은 그대로다.
- `vitest.setup.ts`: `configure({ asyncUtilTimeout: 5000 })`.
  문제 카드가 지연 청크가 되면서 **테스트 파일의 첫 렌더**가 KaTeX 모듈 그래프 적재
  비용을 물게 됐다. 격리 실행은 350ms 인데 전체 실행에서 워커가 CPU 를 다투면 RTL
  기본 상한 1초를 넘겨 첫 테스트만 간헐 실패했다(3회 중 2회 재현 → 조정 후 3회 연속 초록).
  `vitest.config.mts` 가 같은 렌더 스택 때문에 testTimeout 을 5초→20초로 올린 것과
  같은 성질의 조정이다. **깨진 렌더는 여전히 실패한다 — 1초가 아니라 5초 뒤에.**
