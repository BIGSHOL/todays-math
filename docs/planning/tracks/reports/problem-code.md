### 1.2 대단원 번호 — ⚠️ 부류마다 다르다

## §2 배선 — 새 문항이 코드 없이 들어올 경로가 하나도 없음을 보인다

### 2.1 무엇을 골랐나, 왜

**부여는 DB 트리거 한 곳.** 뜻 부분은 **미리 계산해 `unit.problem_code_prefix` 에 저장**.

브리프가 지적한 대로, 앱 코드 세 곳을 각각 고치는 방식은 또 한 곳을 빠뜨린다
(오늘 그림 치수에서 실제로 그랬다). 그래서 부여 지점을 **테이블에** 두었다.

그런데 순수한 Postgres 기본값(`DEFAULT`)만으로는 안 된다 — 뜻 부분이 `unit_id` 를
봐야 하기 때문이다. 그래서 이렇게 갈랐다:

```
«뜻» 부분          «무작위» 부분 · 부여 시점
─────────────────  ────────────────────────────
TypeScript 한 곳    PL/pgSQL 트리거 한 곳
src/lib/problemCode.ts   problem_code_assign / problem_code_next
      ↓ 산출물               ↑
unit.problem_code_prefix ──┘  (읽기만 한다)
```

**왜 이렇게 갈랐나 — 규칙을 SQL 에도 쓰면 두 벌이 되기 때문이다.** 이 저장소가 여러 번
데인 자리다(「세는 쪽과 고치는 쪽이 같이 눈이 먼다」). 이 구조에서 SQL 이 하는 일은
`prefix || '-' || 무작위4` 뿐이라 **의미를 틀릴 여지가 없다.** 덤으로 규칙을 **DB 없이**
시험할 수 있다 — `npm run test` 는 DB 에 붙지 않는다.

대신 SQL 에는 735줄짜리 «답»이 박혀 있다. 그 목록이 지금 규칙과 글자까지 같은지
**테스트가 매번 다시 만들어 대조한다**(`problemCode.test.ts` 마지막 묶음).
한쪽만 고치면 빨개진다.

| 후보 | 왜 안 골랐나 |
|---|---|
| Postgres `DEFAULT` 만 | 뜻 부분이 `unit_id` 를 봐야 해서 불가 |
| TS 단일 진입점 | 우회할 수 있다. 날 SQL·psql·다음 세션의 새 스크립트가 안 지난다 |
| 트리거가 규칙까지 | 규칙이 두 벌이 되고, DB 없이는 시험할 수 없다 |
| **트리거 + 미리 계산한 prefix** | ← 고른 것 |

|---|---|---|

**B4a 가 왜 따로 있나** — B4 만 보면 「같은 씨앗을 심었다」는 전제가 참인지 아무도 확인하지
않는다. `setseed` 가 아예 안 먹어도 두 코드는 다르게 나오고 검사는 초록이 된다.
그래서 씨앗이 정말 되감기는지를 **대조군으로 먼저 확인**하고, 2차가 «첫 뽑기가 아니라
둘째 뽑기»를 받았는지까지 본다. (적대적 리뷰 ④ §H 「지표의 «참»이 어디서 오는가」.)

### 2.4 남은 위험 하나 — **한 INSERT 문 안의 겹침** (조용하지 않다)

트리거의 중복 검사는 `SELECT … WHERE problem_code = v_code` 다. 그런데 **한 문장이 방금
넣은 행은 그 문장의 다음 행에 안 보인다**(같은 스냅샷). 그래서 `createMany` 로 **같은
단원 수백 행**을 한 문장에 넣으면 재시도가 그 겹침을 못 보고, 유니크 인덱스가 잡는다.

- **얼마나?** 32^4 = 1,048,576 자리에서 같은 단원 200행이면 약 **1.9%**, 25행이면 **0.03%**
  [추정 — 생일 문제]. B3 에서 25행은 실측으로 겹치지 않았다.
- **겹치면 어떻게 되나?** **문장이 실패한다.** 조용히 중복이 들어가지 않는다 —
  틀린 코드가 남는 것보다 낫다. 청크를 나눠 다시 넣으면 된다.
- **백필(가장 큰 덩어리 47,152)은 이 위험이 없다** — 행 단위 고리라 앞 행이 보인다(§3).
- **줄이려면**: 적재 청크를 단원 단위로 쪼개거나, 무작위 자릿수를 늘린다(D-53 변경 필요).
  지금은 **고치지 않았다.** 실제 적재는 여러 단원이 섞인 청크라 200행 동단원은 드물고,
  실패해도 시끄럽기 때문이다. 이 문단이 그 판단의 기록이다.

**왜 `gen_random_bytes` 가 아니라 `random()` 인가** — pgcrypto 1.3 은 이 DB 에 설치돼 있다
(브리프 지시대로 다시 확인했다). 그런데 `random()` 은 `setseed()` 로 **되감을 수 있어서**
「겹치면 정말 다시 뽑는가」를 실제로 시험할 수 있다. 시험할 수 없는 가드는 장식이다.
이 코드는 비밀이 아니라 표시용 식별자라 예측 불가능성이 필요 없다 — 필요해지면
`gen_random_bytes` 로 바꾸면 되고, 그때 B4 는 못 돌린다는 것을 알고 바꾸면 된다.

## §3 백필 — 47,152건

```
적용 전:  문항 47,152 · 코드 있음 0 · 빈 값 47,152
적용 후:  문항 47,152 · 코드 있음 47,152 · 빈 값 0
          중복 0 · 형식 위반 0 · 코드 앞부분 없는 단원 0
```

24회차(2,000행씩) · **16초**. 그 뒤 `problem_problem_code_present` 를 `VALIDATE` 해
기존 행까지 검사 대상에 넣었고, 별도 마이그레이션으로 컬럼을 `NOT NULL` 로 굳혔다.

- **드라이런이 기본**, `--apply` 는 `ALLOW_SHARED_IMPORT=1` 이 있어야 열린다(D-31).
- **멱등** — `WHERE problem_code IS NULL` 만 고른다. 이미 있는 행은 `problem_code_freeze`
  트리거가 **바꾸지 못하게 막는다**(멱등이 «관행»이 아니라 «강제»다).
- **새 문항과 같은 함수**(`problem_code_next`)를 쓴다. 백필이 제 규칙을 갖지 않는다.
- **행 단위 고리**(서버 쪽 `DO` 블록)로 돈다. 한 `UPDATE` 문에 몰면 그 문장이 방금 넣은
  코드가 다음 행의 중복 검사에 **안 보인다**(같은 스냅샷) — 같은 단원 수천 행에서 겹칠 수 있다.
- **`updated_at` 을 안 건드린다.** 날 SQL 이라 Prisma 의 `@updatedAt` 이 끼지 않는다.
  일부러 그랬다 — 「적재 후 손댄 행」 신호(39,563건)가 47,152 로 뭉개지면 그 신호가 죽는다.
  백필 뒤 실측 **39,575** 로 그대로다(앞 트랙이 잰 39,563 과 12 차이 — 그 사이 다른 세션이
  손댄 행이다. 47,152 가 아니라는 것이 요점이다).

### 되돌리기

`scripts/qa/reports/problem-code-ledger.json.gz` (47,152건, 1.2MB) — 문항 id ↔ 코드.
**커밋된다**: `.gitignore` 에 예외를 넣고 `git status --porcelain` 으로 실제로 추적되는지
확인했다(옆에 만든 대조용 파일은 무시됨). 코드는 원장님이 종이·대화에 옮겨 적는 값이라
컬럼을 다시 만들 때 **새로 뽑으면 안 된다.**

컬럼째 없애려면 마이그레이션 머리의 DROP 문 8줄(`--revert` 로도 돈다). 순수 추가라
기존 데이터를 한 바이트도 안 건드린다.

## §4 가드를 하나씩 망가뜨렸다

브리프가 시킨 다섯. **하나씩 실제로 코드를 고쳐 돌리고 되돌렸다.**

| # | 무엇을 망가뜨렸나 | 결과 | 빨개진 검사 |
|---|---|---|---|
| 1 | **코드를 파생으로** — PATCH 가 단원이 바뀌면 코드도 맞춰 준다 | 🔴 2건 | 「단원을 다른 대단원으로 옮겨도 코드가 그대로다」 · 「옮긴 뒤 다시 조회해도 같은 코드가 나온다」 |
| 2 | **학교급 문자 뒤섞기** — 초1↔중1 코드 맞바꿈 | 🔴 4건 | 「학교급 문자는 초 E · 중 J · 고 H 다」 · 「초등은 `1-1` 을 대단원 번호로 읽지 않는다」 · 「학교급·학년이 바뀌면 앞 두 자리가 바뀐다」 · 「커밋된 SQL 의 단원 코드 목록이 지금 규칙과 글자까지 같다」 |
| 3 | **무작위 집합에 `0 O 1 I` 넣기** | 🔴 5건 | 「헷갈리는 글자 0 O 1 I l 이 없다」 · 「32자(=2^5)이고 중복이 없다」 · 「헷갈리는 글자가 든 코드는 거절한다」 · 「SQL 이 쓰는 무작위 집합이 계약과 같은 한 벌이다」 · 「SQL 의 형식 검사가 계약의 정규식과 같다」 |
| 4 | **충돌 재시도 없애기** | 🟢→🔴 (아래) | 「충돌 재시도 고리가 있다」 · 「재시도가 다 실패하면 멈춘다」 (+ DB 실측 B10) |
| 5 | **부여 경로에서 코드 빼기** | 🔴 6건 (앱) · 🔴 B9 (DB) | 「등록 응답에 형식을 지키는 코드가 실린다」 · 「두 문항이 같은 코드를 받지 않는다」 외 4건 |

### ⚠️ 변이 4 에서 **가드가 장식이었다** — 망가뜨려 보고서야 알았다

처음 쓴 가드는 이랬다:

```ts
expect(sql).toMatch(/LOOP/);
expect(sql).toMatch(/RAISE EXCEPTION/);
```

**재시도 고리를 통째로 지워도 28개 전부 초록이었다.** 이유는 단순하다 — 무작위 4자를
뽑는 함수에도 `LOOP` 가 있고(`FOR i IN 1..4`), 단원 코드 검사에도 `RAISE EXCEPTION` 이
있다. 그 낱말들은 **재시도와 아무 상관이 없었다.**

고친 것 둘:

1. 텍스트 가드를 **재시도 고리 자체의 모양**으로 좁혔다 —
   `FOR i IN 1..v_tries LOOP` · `PERFORM 1 FROM "problem" p WHERE p."problem_code" = v_code` ·
   `IF NOT FOUND THEN … RETURN v_code`. 이제 지우면 **2건이 빨개진다**(확인함).
2. 텍스트만으로는 부족하므로 **DB 실측 B10** 을 새로 넣었다: 재시도가 **없는** 함수로
   갈아 끼우고 같은 씨앗을 심으면 `23505 Key (problem_code)=(…) already exists` 로 죽는다.
   그래야 B4 의 초록이 「재시도 덕」이라는 뜻이 된다. (전부 ROLLBACK 된다.)

이건 적대적 리뷰 ④ §H 가 상수 29개 중 9개에서 찾아낸 것과 **같은 부류**다.
브리프가 「망가뜨려 보라」고 하지 않았으면 그대로 남았을 것이다.

### 덤 — B10 자체도 처음엔 거짓 빨강이었다

B10 을 B4 와 **같은 씨앗**(0.4242)으로 썼더니 1차부터 죽었다. B4 가 이미 그 코드를
넣어 뒀기 때문이다 — 「재시도가 없어서 겹쳤다」가 아니라 「앞 검사의 행과 겹쳤다」였다.
씨앗을 갈랐고, 판정 문구도 **1차가 왜 실패했는지 구분해서** 찍게 고쳤다.

## §5 안 한 것 — 왜

### 5.1 화면 (브리프가 명시적으로 이 세션 밖으로 뺐다)

D-53 은 「화면은 코드 옆에 **현재 단원·출처를 항상 같이** 보여야 한다」고 정했다.
그게 **코드가 거짓말하는 것을 사람이 알아챌 유일한 길**이다 — 뜻 부분은 스냅샷이라
단원 재배정 뒤에는 지금 단원과 다르다.

**그런데 놓을 자리가 없다** — `/problems/[id]` 한 문항 화면이 아직 없다
(`id-find-review.md` §3 ②). 브리프가 「값을 만들고 API 가 내보내는 데까지만」으로 잘랐고
그대로 따랐다. 지금 목록 화면에 코드를 얹지 않은 것도 D-07(형태는 원장님 확정) 때문이다.

**남은 일**: ⑴ `/problems/[id]` 한 문항 화면, ⑵ 그 화면의 「코드 + 현재 단원 + 출처」 배치
(D-07 확정 필요), ⑶ 코드로 문항을 찾는 길(`id-find` §5.3), ⑷ 지면 표시 여부
(`id-print` §8 Wire A~G — 원장님이 A~G 중에서 고르실 일).

### 5.2 `externalId` 는 손대지 않았다

D-53·`id-scheme-review` 권고 2 그대로다. 승격도 삭제도 형식 통일도 안 했다.
그것은 **이관 멱등 키**이고 우리 밖(변환기 색인 rowid)을 가리킨다.

### 5.3 `prisma migrate deploy` 를 쓰지 않았다

이 저장소에 **다른 트랙의 미적용 마이그레이션이 하나** 있다
(`20260817120000_problem_created_at_indexes` — 그 파일 머리에 「공유 Supabase 에는 적용하지
않았다」고 적혀 있다). `deploy` 는 그것까지 같이 적용한다. **남의 결정을 대신 내리지 않으려고**
이 마이그레이션 둘만 적용하고 `_prisma_migrations` 에 같은 방식으로 기록했다
(체크섬 = CR 제거 후 sha256 — 기존 행과 대조해 실측으로 확인한 규칙이다).

→ **남은 일**: 그 인덱스 마이그레이션을 공유 DB 에 적용할지는 그 트랙이 정할 일이다.
`npx prisma migrate diff` 에 지금 유일하게 남는 차이가 그것이다(내 컬럼·제약은 차이 0).

## §6 이 작업에서 내가 틀렸던 것 (기록으로 남긴다)

1. **확인용으로 넣은 행을 지우지 않았다.** 마이그레이션 적용기의 「트리거가 붙는지」
   확인은 드라이런에서는 통째로 ROLLBACK 되지만 `--apply` 에서는 **커밋된다.**
   그 자리를 빠뜨려 공유 DB 에 문항 한 개(`E10101-9CPQ`)가 남았다. 바로 찾아 지웠고
   (`content = '드라이런'` 1건), 스크립트가 넣은 행을 **반드시 지우도록** 고쳤다.
   → 교훈: **드라이런에서 안전한 코드가 `--apply` 에서도 안전한 것은 아니다.**
2. **실패를 기대하는 검사를 트랜잭션 안에 그냥 넣었다.** PostgreSQL 은 한 문장이 실패하면
   그 트랜잭션이 통째로 못 쓰게 된다(25P02). 그래서 B5 이후 검사가 **전부 죽었다** —
   초록도 빨강도 아니고 그냥 안 돌았다. `SAVEPOINT` 로 감쌌다.
   → 교훈: **실패를 기대하는 검사는 실패 뒤에도 계속 돌 수 있어야 «검사»다.**
3. **B4 를 처음엔 동어반복으로 썼다.** 「같은 씨앗으로 두 번 넣었더니 코드가 다르다」는
   `setseed` 가 아예 안 먹어도 참이다. 대조군(B4a)을 넣고 나서야 검사가 됐다.
4. **재시도 가드가 장식이었다** — §4 참조. `LOOP`·`RAISE EXCEPTION` 이라는 흔한 낱말을
   세고 있었고, 재시도를 통째로 지워도 28개 전부 초록이었다. **가장 큰 것**이라
   CLAUDE.md Lessons Learned 에도 남겼다.
5. **`/api/units` 가 컬럼 하나에 500 이 될 뻔했다.** 그 라우트는 `db.unit.findMany()` 결과를
   통째로 `as UnitEntity[]` 로 우겨넣는데 계약이 `strictObject` 라, `problem_code_prefix` 를
   넣자마자 응답이 깨졌다(테스트가 잡았다). 계약에 있는 다섯 개만 `select` 하도록 고쳤다 —
   **이제 컬럼이 늘어도 그 라우트는 안 깨진다.** 원래 있던 결함을 이번에 밟은 것이다.
