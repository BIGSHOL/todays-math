## 1. 🔴① 그림 높이를 판정에 넣었다 — 재현율 30.4% → 96.3%

**커밋** `c3e9a1c6`

`estimateProblemLines(content)` 의 **인자에 그림이 아예 없었다.** 그림을 보는 규칙은
`OVERFLOW_FIGURE_LIMIT = 2` 하나뿐인데 실데이터 그림 문항의 94%가 1장짜리다.
**인자에 없는 것은 임계값을 어떻게 옮겨도 안 잡힌다** — 리뷰가 한계를 14에서 8까지
내려도 전수 재현율이 50%를 못 넘는 것을 보였다.

### 자 — 그림 묶음 높이 모형 (`estimateFigureBlockPx`)

지면(`ProblemContent`)을 그대로 옮겼다:

- `print:max-w-[70mm]`(264.567px) 를 넘으면 **비율대로** 축소
- `flex-wrap` — 가로로 늘어놓다 문항 열(363.5px)을 넘으면 다음 줄
- `items-start` — 한 줄의 높이는 그 줄에서 **가장 높은 장**
- `gap-4`(16px) 는 가로·세로 모두, `mt-3`(12px) 는 묶음 위

**실측과 100%가 2px 이내로 맞는다**(치수를 아는 8,442건, 오차 중앙 0.0px).
근사가 아니라 기하다 — 그래서 맞는다.

### 치수는 DB 에 넣었다

판정은 브라우저에서 돌아 판정 시점에 이미지 파일을 못 읽는다. 원본 치수는 적재 때
한 번 읽으면 되는 값이라 컬럼이 맞다.

```
마이그레이션  20260818120000_problem_figure_dims
              ALTER TABLE problem ADD COLUMN figure_dims INTEGER[] NOT NULL DEFAULT '{}'
형식          figure_urls 와 같은 순서로 짝지은 [w1,h1,w2,h2,…] 평탄 배열
추출          scripts/qa/extract-figure-dimensions.ts  — PNG/JPEG 머리만 읽는다
              (9,587장 전량 100% 확보 · 275MB 를 디코딩하지 않는다)
적재          scripts/qa/backfill-figure-dimensions.ts — 드라이런이 기본,
              ALLOW_SHARED_IMPORT=1 --apply 로만 열린다. 8,442건 적재.
              재실행 시 「쓸 것 0 · 이미 같음 8,442」 (멱등)
되돌리기      --revert (전량 빈 배열)  또는  ALTER TABLE problem DROP COLUMN figure_dims;
```

기존 데이터를 한 바이트도 안 건드리는 **순수 추가**다. 기본값이 카탈로그에 저장되므로
47,152행을 다시 쓰지 않는다(PostgreSQL 11+). 공유 DB 의 다른 마이그레이션
(`20260817120000_problem_created_at_indexes`, 「공유 Supabase 에는 적용하지 않았다」고
적혀 있는 것)은 **건드리지 않았다** — `db execute` + `migrate resolve --applied` 로
이 한 건만 적용했다.

### 치수를 아는 것이 실제로 값을 하는가 — 적재 전에 쟀다

공유 DB 를 건드리기 전에 `--dims-file` 로 「알면 얼마나 좋아지는가」를 먼저 쟀다:

```
같은 한계에서   치수 모름(보수적 상수 207px)  재현율 59.0%
                치수 앎(적재 후)              재현율 96.3%
```

적재가 **37%p** 를 낸다. 그 확인 뒤에 썼다.

### 곁가지 — 그림 **장수** 규칙은 안전망으로 내렸다

치수를 알면 높이 규칙이 같은 문항을 이미 본다. 실측으로 「장수만 걸리는」 39건은
**한 건도 안 넘쳤다.** 그래서 `figureCount >= 2` 는 **치수를 모를 때만** 켜진다.

  «뒤로 옮기는 것»이고, 사유가 가리키는 곳이 곧 손볼 곳이어야 한다.

## 3. 🔴④ 정답지도 판정한다 — 재현율 0% → 97.7%

**커밋** `b2ae12b9`

`assessOverflowRisk` 는 `content` 만 읽고 **`solution` 은 한 글자도 안 봤다.**
`.answerSolutions` 는 `column-count:2` + `overflow:hidden` 이라 높이를 넘긴 해설은
**3번째 단으로 밀려 지면 밖에서 사라진다** — 부분 잘림이 아니라 **한 문항의 해설이
통째로 없어진다.**

`assessAnswerKeyRisk(problems)` 를 새로 두고, 쪽마다 2단을 실제로 채워 보며
«어느 쪽에서 어느 문항이 3번째 단으로 밀리는가»를 낸다(`break-inside: avoid` 라
단 경계에서 안 쪼개지고 통으로 넘어간다). 화면에는 문제지 경고와 **별도 줄**로 나간다.

### ⚠️ 여기서 한 번 크게 틀렸다 — 이번 수리의 교훈

처음에는 「빠른 정답」 상자를 **합성 정답 「1」 로, 지면 밖에서 따로 떼어** 재서
「25문항 = 344.7px」 로 굳혔다. 실제 정답은 수식이라 셀이 두세 줄로 접히고,
지면에서 다시 재니 같은 25문항 상자가 **344~668px** 로 갈렸다.

그만큼 1쪽 해설 칸을 **139px 넓게** 봤고, 재현율이 **52.3%** 에 머물렀다.
측정을 **실제 내용으로, 실제 지면 안에서** 다시 하니 **97.7%** 가 됐다.

> **지면을 재려면 실제 내용으로, 실제 지면 안에서 재라.** 합성 입력으로 따로 떼어 재면
> 그 값은 «가장 좁은 경우»가 되고, 판정은 그만큼 조용해진다.

`measure-answerkey-overflow.tsx` 는 이제 장 단위 «잘렸다»뿐 아니라
**문항 단위 «지면 밖으로 밀렸다»**와 항목·셀 높이까지 같이 낸다. 채점은 그 문항 단위로 한다.

### 해설 높이의 자

| 무엇                           | 값                 | 근거                   |
| ------------------------------ | ------------------ | ---------------------- |
| 한 단에 들어가는 표시폭        | 52 단위            | 해설 3,000건 격자 탐색 |
| 해설 한 건의 고정 세로         | 48px               | 제목 줄 + 마진         |
| **세로로 자리를 더 먹는 수식** | 개당 +4px          | 분수·Σ·∫·행렬·cases    |
| 렌더러와 같은 정규화           | `normalizeOcrText` | ↓                      |

`normalizeOcrText` 를 태우는 것이 결정적이다. DB 해설에는 OCR 이 수식마다 빈 줄을 넣어
«문단»이 100개 넘는 것이 있는데 렌더러는 그 개행을 **전부 공백으로 녹인다.**
문단으로 세면 실측 309px 짜리를 **2,098px** 로 본다 — 실제로 그렇게 틀렸다가 고쳤다.

세로 수식 항을 넣으면 오차 |20px| 이내가 80.7% → **86.3%**, 20px 넘게 **과소평가**하는
비율이 13.5% → **7.3%** 로 준다. 과소평가가 곧 놓침이라 정확도보다 이쪽이 중요하다.

## 4. 🔴② 경고가 실제로 일어나는 일을 가리킨다

**커밋** `a93e2315`

**주석이 코드보다 오래 살았다.** 두 파일 머리 주석이 「`.problemBox` 에
`overflow: hidden` 이 걸려 있어 잘린다」고 적었는데 **그런 클래스는 없다.**
CSS 의 `overflow: hidden` 은 `.a4Page` 와 `.answerSolutions` 둘뿐이고
문항 칸 `.problemItem` 에는 없다. 그래서 실제로는

- 1번 문항이 넘치면 **2번 문항 위에 겹쳐 찍히고**,
- 2번 문항이 넘치면 **보기·정답란이 지면 밖으로 밀려 사라진다**(다음 장으로 안 간다).

예전 문구 「잘리지 않았는지 확인하십시오」는 **원장에게 없는 것을 찾으라는 말**이다.
찾는 대상이 틀리면 경고가 있어도 지나친다.

```
전  지면을 넘길 수 있는 문항이 있습니다 — … 인쇄 미리보기에서 잘리지 않았는지 확인하십시오.
후  지면을 넘겨 옆 문항과 겹쳐 인쇄될 수 있는 문항이 있습니다 — … 인쇄 미리보기에서
    글자가 겹치거나 보기·정답란이 빠지지 않았는지 확인하십시오.
```

**다시 썩지 않게 잠갔다** — CSS·UI **원문**을 읽어 넷을 대조한다
(`.problemBox` 부재 · `.problemItem` 에 overflow 없음 · `overflow:hidden` 주인이
정확히 둘 · 경고 문구가 «잘림»을 찾으라고 하지 않음).

## 5. 🟡⑤ «자»와 한계를 같이 고쳤다

**커밋** `d1e61318`

자가 지면과 **한 방향으로** 어긋나 있었다 — 전부 덜 셌으므로 오차가 상쇄되지 않았다.

| 무엇                           | 지면 실측               | 예전 추정           |
| ------------------------------ | ----------------------- | ------------------- |
| 문항번호 + 정답란              | 62.5px = 3.08줄         | **0줄** (모든 문항) |
| 상자 하나 (`my-4` 포함)        | 98.0px = 4.82줄         | 3줄 = 60.9px        |
| 문항 열 / 1열 보기 / 상자 항목 | 58.2 / 55.2 / 52.7 단위 | **전부 59단위**     |
| 보기 그리드 `mt-4` + 행 간격   | 16px + 8px×n            | 0                   |

### 자를 px 로 바꿨다

`estimateProblemPx` 가 **문항번호 위부터 정답란 아래까지** — 즉
`measure-print-overflow.tsx` 가 재는 구간과 **같은 구간**을 낸다. 그래야 칸과 직접
견줄 수 있고 한계를 유도할 수 있다. `estimateProblemLines` 는 그걸 행높이로 나눈 값이다.

실측 표본 6개 중 **4개가 오차 0.0px**, 나머지 둘은 +6·+8px(보수적).
전수 47,152건에서 오차 **중앙 0px**.

### 한계는 칸 높이에서 유도한다

```
이어지는 장  floor(484 / 20.3125) = 23
첫 장        floor(405 / 20.3125) = 19        (차 4 = round(79 / 20.3125))
```

값의 내력: **14**(폭 규칙과 «같은 경고 건수»로 맞춘 값) → **18**(그림을 세게 된 뒤
실측 곡선의 무릎) → **23·19**(유도).

### 순서를 지켰다

자만 고치고 한계 18을 두면 경고가 **8,446건 · 정밀도 32.3%** 로 튄다.
둘을 같이 옮기니 경고가 오히려 **줄고**(3,742 → 3,495) 첫 장 재현율은 **4.4%p 올랐다.**

```
                      이어지는 장 484px              첫 장 405px
수리 전   경고 1,450  재현율 30.4% 정밀도 57.1%    재현율 19.4% 정밀도 79.4%
①②까지   경고 3,742  재현율 96.3% 정밀도 70.1%    재현율 93.9% 정밀도 78.0%
⑤ 이후    경고 3,495  재현율 96.1% 정밀도 75.0%    재현율 98.3% 정밀도 80.6%
```

### 곁가지 — 「문단 사이 8px」은 존재하지 않는다

`@tailwindcss/typography` 가 설치돼 있지 않아 `prose-p:my-2` 가 빌드 산출물에 한 줄도
없다(리뷰 §8, 실측 0px). 예전 주석이 「8px 이라 안 센다」고 적었는데 그 8px 은 없다.
세지 않은 것은 결과적으로 맞았고, 주석만 사실대로 고쳤다.

### 곁가지 — 측정 도구도 같이 고쳤다

`measure-paper-units.tsx` 가 예전에는 «본문만 잰 높이»와 «고정 chrome 을 포함한 추정»을
견줬다. 자를 고친 직후 **4줄씩 어긋나 보여** 잠깐 헷갈렸다. 이제 같은 구간끼리 견준다.
**세는 쪽과 고치는 쪽이 같은 것을 재는지 먼저 볼 것.**

## 6. 🟡⑥ 2열 과잉의 원인 — `OPERATOR_EXTRA` 가 아니었다 (제안만)

**커밋** `ea6cec81` · **제품 코드 변경 없음**

### `OPERATOR_EXTRA` 는 기여자이지만 «고칠 자리»가 아니다

과잉으로 판정된 38개 중 **36개**에 연산자가 붙어 있고 평균 2.55개(=7.7단위)다.

```
+3 (현행)  과잉 38 · 놓침 14        +2    과잉 16 · 놓침 16
+1.5       과잉 15 · 놓침 18        +0    과잉 12 · 놓침 60
```

놓침(접힘)은 원장님이 2026-08-18 에 직접 지적한 결함이라 늘릴 수 없다.
**`OPERATOR_EXTRA` 자체가 문턱이다** — 여기서 또 문턱을 옮기면 같은 자리를 맴돈다.

### 진짜 자 오류: 「위아래로 쌓이는 것」을 가로 폭으로 센다

- `\frac{a}{b}` 는 분자·분모가 쌓이므로 폭이 `max(|a|,|b|)` 인데 `|a|+|b|` 로 센다.
- `\begin{pmatrix}…\end{pmatrix}` 는 격자인데 **모든 칸을 한 줄로 이어** 센다.
  실측 `$\begin{pmatrix} 6 & 21 \\ 3 & 12 \end{pmatrix}$` 는 **47px** 인데 32단위
  (= 200px)로 본다. **4배 넘게** 부풀린다.

이쪽을 깎으면 **놓침이 한 건도 안 늘고** 과잉만 준다:

```
분수 −1 · 행렬 −16      과잉 38 → 29 · 놓침 14 → 14
+ 순환소수 +6 → +0      과잉      → 25 · 놓침      → 14
문항 단위               1열 94건 중 «2열에 다 들어감» 10 → 7 (접힘 4 그대로)
```

전수 환산 약 **90문항**이 이유 없이 세로로 길어지던 것을 되돌린다.

### 왜 안 고쳤나

`displayWidth` 를 고치면 `fitsTwoColumns` 가 바뀌고, 그건 **인쇄물 출력 결과가 달라지는
변경**이다(절대 규칙 6 — 실물 프린터 검수 대상). 이 트랙의 지시가
「인쇄물 출력 결과가 달라지는 변경은 제안으로 남겨라」이므로 근거만 만들었다.

**제안 (원장님 확정 후 별도 트랙)** — `src/lib/math/displayWidth.ts` 의 `mathGlyphs` 에서
`\frac{…}{…}` 는 분자·분모 중 **넓은 쪽만** 세고, `\begin{…matrix}`·`\begin{array}`·
`\begin{cases}` 는 `\\` 로 나눈 **행 중 가장 넓은 행만** 센다.
순환소수 보정(+6 → 0)은 과잉을 38 → 34 로 줄이지만 **표본이 얇다**(과잉 38개 중
순환소수가 있는 것은 7개, 전체 평균 0.00개) — **낮은 확신**이라 원본 보정 근거(실측
`$0.\dot{5}=0.555555555$` 185px)와 함께 따로 재검할 것.

## 7. 원장님 확정이 필요한 것 (지면 배치 · D-07)

판정으로 못 막는 둘이 남았다. 둘 다 고치면 **인쇄물의 문항 배치가 바뀐다.**
재현물 `_adv-print-overflow.test.ts` 에 **빨간 채로** 이유와 함께 남겨 두었다.

### ⑴ 첫 장 정원 — 문제지

첫 장 칸이 79px 좁은데 `packProblems` 는 첫 장에도 두 문항을 넣는다.
판정은 이제 알아서 경고를 내지만, **1·2번 자리에 놓인다는 사실 자체**는 안 바뀐다.

> **제안**: 첫 장만 1문항으로 줄인다. 25문항 시험지 기준 장 수가 13 → 14 로 는다.
> 첫 장에서만 넘치는 3,216건이 사라진다.
> **대안**: 첫 장의 「◆ 핵심 개념 정리」 상자를 접을 수 있게 하거나 높이를 줄인다
> (79px 중 대부분이 그 상자다). 장 수가 안 늘어난다.

### ⑵ 정답지 1쪽 정원

1쪽에는 「빠른 정답」 상자가 얹히는데 정원은 8건 고정이다. 상자는 문항 수와 **정답의
길이**에 비례해 커진다(실측 25문항에서 **344~668px**). 잘린 134장 중 **95장이 1쪽**이다.

> **제안**: 1쪽 정원을 상자 높이에 따라 줄인다(`assessAnswerKeyRisk` 가 이미 그 높이를
> 계산하므로 같은 함수를 쓰면 된다). 25문항 기준 1쪽 정원 8 → 5~6.
> **대안**: 「빠른 정답」 상자를 **별도 쪽**으로 뺀다. 정답지가 한 장 늘지만
> 해설 쪽은 전부 964.8px 칸을 온전히 쓴다.

### ⑶ 2열 판정의 자 (§6)

위 §6 의 제안. 인쇄물 출력 결과가 달라지므로 실물 검수 대상이다.

# 지면 높이는 한 번만 재고 (전수 약 17분)

`.measure/` 는 gitignore 다 — 재생성 가능하고 수 MB 다.

### 채점기가 제품과 갈라지지 않게

`eval-overflow-rules.ts` 는 **매 실행** 자기 판정과 `assessOverflowRisk` 를 전수 대조하고
한 건이라도 다르면 멈춘다. 실제로 이번에 두 번 걸렸다(그림 장수 규칙을 조건부로 바꿨을 때,
장을 아는 판정을 넣었을 때). **세는 쪽과 고치는 쪽이 같이 눈이 머는 것**을 막는 장치다.

### 캐시가 낡지 않았음을 확인했다

판정만 고치는 동안 지면은 안 바뀌므로 높이 캐시를 다시 쓴다. 그게 참인지 마지막에
**새로 2,000건을 다시 재서** 대조했다 — **다른 것 0건, 최대 차 0.0px.**

## 10. 이번에 되풀이된 교훈

- **지면을 재려면 실제 내용으로, 실제 지면 안에서 재라.** 「빠른 정답」 상자를 합성 정답
  「1」 로 따로 떼어 재서 344.7px 로 굳혔더니 실제(344~668px)보다 좁게 봤고, 1쪽 해설 칸을
  139px 넓게 봐서 재현율이 52.3% 에 머물렀다. 실제 지면에서 다시 재니 97.7% 가 됐다.
  §1 의 함정 4(칸을 grid row 로 재면 넘침이 영원히 0)와 **같은 부류**다 —
  둘 다 «편한 자리에서 잰 값»이 조용히 관대한 쪽으로 기울었다.
- **인자에 없는 것은 임계값을 옮겨도 안 잡힌다.** 그림이 그랬다. 재현율 30.4%는 문턱이
  나빠서가 아니라 그림이 인자에 없어서였다 — 한계를 8까지 내려도 50%를 못 넘는다.
- **문턱을 옮기면 안 되는 게 아니라, 옮기려는 그 값이 이미 문턱일 수 있다.**
  `OPERATOR_EXTRA` 가 그랬다. 3 → 2 는 과잉 38 → 16 이지만 놓침 14 → 16 으로 맞바꾼다.
  진짜 자 오류(쌓이는 수식을 가로로 셈)를 고치면 놓침이 **한 건도 안 늘고** 과잉만 준다.
- **자와 한계는 같이 움직인다.** 자만 고치면 경고가 8,446건(정밀도 32.3%)으로 튀고,
  한계만 옮기면 덜 세던 몫이 되살아난다. 같이 고치니 경고가 **줄면서** 재현율이 올랐다.
- **세는 쪽과 고치는 쪽이 같은 것을 재는지 먼저 보라.** `measure-paper-units.tsx` 가
  «본문만 잰 높이»와 «고정 chrome 을 포함한 추정»을 견주고 있어서, 자를 고친 직후
  4줄씩 어긋나 보였다. 도구를 고쳐야 할 자리였다.
- **주석이 코드보다 오래 산다.** `.problemBox` 한 줄이 「잘림」이라는 틀린 그림을
  테스트 이름과 경고 문구까지 퍼뜨렸다. 이제 CSS·UI **원문**을 읽어 잠근다.
