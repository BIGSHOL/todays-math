### 실데이터 검증 — 합성 픽스처만 믿지 않았다

직전 회차에 합성 픽스처가 이관 결함을 통과시킨 전례가 있어(tracks/README.md), 실측 코퍼스로 전수 검증했다.
`PREDICTOR_CORPUS_DIR` (handoff-a-index) 의 추출본을 신뢰 가드(11 §11)로 거른 뒤,
각 학교의 **실제 배점 눈금**으로 보정기를 돌렸다.

```
신뢰 가드 통과 코퍼스        1,448 편
검사 조합 (문항 수 −2 / 0 / +3)  4,344 건
합계 정확히 100 달성          4,272 건 (98.3%)
판단 불가 (합계_100_불가)        72 건
눈금 밖 배점                     0 건
합계가 100 이 아닌 결과            0 건
"만들 수 있는데 못 만든다"고 한 것   0 건  ← 독립 DP 로 교차 검증
```

72건은 **그 눈금 집합과 그 문항 수로는 100 이 원리적으로 불가능한 조합**이다(예: 최고 눈금 12점 ×
8문항 = 96점). 억지로 눈금 밖 값을 지어내는 대신 판단 불가를 돌려준다.
이 테스트는 코퍼스가 없는 컴퓨터에서는 **조용히 건너뛴다** — 다른 트랙 CI 를 이 경로로 깨지 않는다.
원본 코퍼스는 **읽기만** 했다.

## 3. 문서에 없어서 내가 정한 것 (코디네이터 확인 필요)

§10.3 은 산식 5줄이 전부라, 실제로 돌리려면 아래를 정해야 했다. **임의로 바꾼 것이 아니라 없던 것을
채운 것**이고, 각 파일 머리 주석에 근거를 남겼다. 원장님/코디네이터가 뒤집을 수 있는 지점이다.

1. **0.01점 단위 정수 연산.** 눈금이 소수(3.2·2.5·3.75)라 실수 덧셈으로는 합이 100 이 안 된다.
   0.01 로 안 떨어지는 눈금(3.333 등)은 `눈금_해상도_초과` 로 돌려준다. 실측 코퍼스에는 그런 눈금이
   **0건**이었다(위 검증에서 확인).
2. **§10.3-4 "내림"이 최저 눈금 아래로 갈 때는 최저 눈금으로 둔다.** 그보다 낮은 값은 그 학교 눈금이
   아니므로 지어내는 것이 된다.
3. **1차 배정 합이 100 을 넘는 경우**(그 학교 눈금 평균 × 문항 수 > 100)가 실제로 생긴다.
   §10.3-5 를 대칭으로 뒤집어 잔여가 **작은** 문항부터 한 눈금씩 내린다. 동점이면 번호가 **작은** 쪽부터
   — "큰 번호에 먼저 준다"의 대칭이다.
4. **최대잉여법이 100 에 정확히 못 닿는 경우가 남는다**(눈금 간격이 성겨 남은 점수가 어떤 한 눈금
   상승에도 안 맞는 경우). 이때만 도달 가능성 DP 를 돌려 ① 애초에 가능한 조합인지 판정하고
   ② 가능하면 §10.3 우선순위(잔여 큰 순)를 지키면서 100 으로 닫는다. **최대잉여법이 이미 100 을
   맞췄으면 이 단계는 아무것도 바꾸지 않는다(no-op).** 즉 §10.3 의 결과를 덮어쓰지 않는다.
5. **라벨 없는 문항(실측 14%)** 은 순위만 가운데로 두고, 난이도 값을 "중"이라고 **기록하지는 않는다.**
6. **예측 문제지의 칸 배치**: 유형은 객관식→단답형→서술형, 난이도는 하→중→상 순. 학교별로 배우지
   않는다 — 번호별 난이도 곡선은 학교 고유성이 4.4% 뿐이라 학교별 학습은 잡음을 패턴으로 착각한다
   (11 §2.2). 실측 대구여고 1639 원본도 객관식 17(3.5~4.2) + 서술형 4(7·8·10·10) 배치였고,
   보정기가 같은 배치를 냈다.
7. **§L6 우선순위 ①②의 순서를 하나 뒤집었다.** 문서 목록은 ①(학교 재출제)이 맨 앞이지만, 구현은
   **칸 일치(②)를 먼저 보고 그 안에서 ①을 우선**한다. ①을 무조건 앞에 두면 단원·난이도가 어긋나는
   재출제 문항이 맞는 칸을 밀어내 시험 범위가 깨진다. **이 판단은 뒤집힐 수 있다 — 확인 바란다.**

## 4. 막힌 것 / 안 한 것

- **DB 에 쓰는 경로는 만들지 않았다.** 두 함수 모두 순수 함수이고, `TestProblem.score` 에 실제로
  적재하는 코드는 없다. 지시서가 준 소유 파일이 계약 1 + 라이브러리 2 뿐이라 Route Handler·
  저장 로직은 내 범위 밖으로 봤다. **다음 태스크가 필요하다.** 스키마는 이미 준비돼 있다
  (`TestProblem.score Float?`) — 없는 컬럼은 없었다.
- **화면(수동 조정 UI)은 만들지 않았다.** D-07(디자인 정체성, 원장님 확정 절차)이 걸려 있고
  `05-design-system.md §8.7` 확정 여부를 내가 판단할 수 없다. `validateManualScores` 가 화면이
  쓸 검증 함수와 문구(`합계 98.5 — 1.5점 남음`)까지 내주므로, 화면은 이 함수를 부르기만 하면 된다.
- **"유사한 문항"(§L6 ①)을 같은 문항 재출제로만 봤다.** 문항 유사도 엔진이 아직 없다.
  유사도가 생기면 `composePredictedPaper` 의 선택 키에 한 항을 더하면 된다.
- **후보 배정은 탐욕법**(정확 일치 1차 → 완화 2차)이다. 최적 이분매칭이 아니라, 드물게 완전 배정이
  가능한데도 `unfilled` 이 남을 수 있다. 실데이터에서 결손이 잦으면 헝가리안 매칭으로 바꾸는 것이
  다음 단계다.
- **`Problem.questionType` 이 NULL 인 문항**은 유형 일치를 확인할 수 없어 `relaxed` 에 `유형` 을
  남긴다. T7.6 백필이 끝나면 자연히 줄어든다 — 지금은 "맞았다고 치지" 않는 쪽을 택했다.

## 5. 코디네이터가 확인해야 할 것

1. **§3의 7번(우선순위 ①②를 뒤집은 것)** — 원장님 의도가 "재출제를 무조건 먼저"라면 되돌려야 한다.
2. **판단 불가를 어떻게 화면에 보여줄지.** 실측상 2%가 `합계_100_불가` 로 나온다. "문항을 더 넣어
   달라"는 안내가 맞는지, 아니면 그 학교 눈금 밖 값을 허용할지는 제품 결정이다.
   (지금은 **지어내지 않는 쪽**으로 고정했다.)
3. **`TestProblem.score` 적재 태스크의 소유자.** 위 4번 첫 항목.
4. `npx prisma generate` 미실행으로 기준선 테스트 2건·타입 오류 83건이 나던 문제 —
   다른 트랙 워크트리도 같은 상태일 수 있다.
