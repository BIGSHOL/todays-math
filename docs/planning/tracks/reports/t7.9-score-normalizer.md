### 실데이터 검증 — 합성 픽스처만 믿지 않았다

직전 회차에 합성 픽스처가 이관 결함을 통과시킨 전례가 있어(tracks/README.md), 실측 코퍼스로
전수 검증했다. `PREDICTOR_CORPUS_DIR` 의 추출본을 신뢰 가드(11 §11)로 거른 뒤, 각 학교의
**실제 배점 눈금**으로 보정기를 돌렸다.

```
신뢰 가드 통과 코퍼스           1,448 편
검사 조합 (문항 수 −2 / 0 / +3)   4,344 건
합계 정확히 100 달성            4,272 건 (98.3%)
판단 불가 (합계_100_불가)           72 건
눈금 밖 배점                        0 건
합계가 100 이 아닌 결과              0 건
"만들 수 있는데 못 만든다"고 한 것    0 건  ← 독립 DP 로 교차 검증
```

72건은 **그 눈금 집합과 그 문항 수로는 100 이 원리적으로 불가능한 조합**이다(예: 최고 눈금
12점 × 8문항 = 96점). 억지로 눈금 밖 값을 지어내는 대신 판단 불가를 돌려준다.
이 테스트는 코퍼스가 없는 컴퓨터에서는 **조용히 건너뛴다**. 원본 코퍼스는 **읽기만** 했다.

적재 부분은 구현을 먼저 쓴 뒤 테스트를 붙였으므로, 테스트가 실제로 무는지 직접 확인했다.

## 3. 문서에 없어서 내가 정한 것

§10.3 은 산식 5줄이 전부라, 실제로 돌리려면 아래를 정해야 했다. **임의로 바꾼 것이 아니라 없던
것을 채운 것**이고, 각 파일 머리 주석에 근거를 남겼다.

1. **0.01점 단위 정수 연산.** 눈금이 소수(3.2·2.5·3.75)라 실수 덧셈으로는 합이 100 이 안 된다.
   0.01 로 안 떨어지는 눈금은 `눈금_해상도_초과`. 실측 코퍼스에는 그런 눈금이 **0건**이었다.
2. **§10.3-4 "내림"이 최저 눈금 아래로 갈 때는 최저 눈금으로 둔다.** 그보다 낮은 값은 그 학교
   눈금이 아니므로 지어내는 것이 된다.
3. **1차 배정 합이 100 을 넘는 경우**가 실제로 생긴다. §10.3-5 를 대칭으로 뒤집어 잔여가
   **작은** 문항부터 내린다. 동점이면 번호가 **작은** 쪽부터.
4. **최대잉여법이 100 에 정확히 못 닿는 경우**에만 도달 가능성 DP 를 돌려 100 으로 닫는다.
   **최대잉여법이 이미 100 을 맞췄으면 아무것도 바꾸지 않는다(no-op)** — §10.3 결과를 덮어쓰지 않는다.
5. **라벨 없는 문항(실측 14%)** 은 순위만 가운데로 두고, 난이도 값을 "중"이라고 **기록하지는 않는다.**
6. **예측 문제지의 칸 배치**: 유형은 객관식→단답형→서술형, 난이도는 하→중→상. 학교별로 배우지
   않는다 — 번호별 난이도 곡선은 학교 고유성이 4.4% 뿐이다(11 §2.2). 실측 대구여고 1639 원본도
   객관식 17(3.5~4.2) + 서술형 4(7·8·10·10) 배치였고, 보정기가 같은 배치를 냈다.
7. ~~§L6 우선순위 ①②의 순서를 뒤집었다~~ → **코디네이터 확인 완료, 그대로 유지.**
   칸 일치(②)를 먼저 보고 그 안에서 학교 재출제(①)를 우선한다.

## 4. 안 한 것 / 남은 것

- **화면은 만들지 않았다.** D-07(디자인 정체성 확정 절차)이 선행이다. API 는 §7 에서 붙였으므로
  화면은 이 두 엔드포인트를 부르기만 하면 된다.
- **`TestProblem.score` 를 API 응답에 노출하지 않았다.** `serializeTestProblemItem` 과
  `testProblemItemSchema` 를 고쳐야 하는데 공용 계약이라 손대지 않았다. 인쇄 지면에 배점을
  띄우는 것 자체가 D-28("배점 없음 — 맞은 개수/전체")과 충돌하므로 **원장님 결정 사항**이다.
- **"유사한 문항"(§L6 ①)을 같은 문항 재출제로만 봤다.** 문항 유사도 엔진이 아직 없다.
- **후보 배정은 탐욕법**(정확 일치 1차 → 완화 2차)이다. 최적 이분매칭이 아니라, 드물게 완전
  배정이 가능한데도 `unfilled` 이 남을 수 있다. 결손이 잦으면 헝가리안 매칭이 다음 단계다.
- **`Problem.questionType` 이 NULL 인 문항**은 유형 일치를 확인할 수 없어 `relaxed` 에 `유형`
  을 남긴다. T7.6 백필이 끝나면 줄어든다 — 지금은 "맞았다고 치지" 않는 쪽을 택했다.

## 5. 코디네이터가 확인해야 할 것

1. **`TestType` enum 에 `predicted` 가 없다.** 예측 문제지를 `review`(확인테스트)로 저장했다.
   구분이 필요하면 마이그레이션이 필요한데, 병렬 세션 충돌을 피하라는 지시가 있어 넣지 않았다.
   **스키마를 고치지 말고 보고하라고 해서 보고한다.**
2. **보정을 거치지 않은 일일/확인테스트는 여전히 만점이 100 이 아닐 수 있다.**
   `TestProblem.score` 가 NULL 이면 옛 규칙(`Problem.score ?? 균등배분`)이 그대로 돌고,
   기출+자작을 섞으면 §10.1 버그가 그대로 난다. 고치지 않은 이유는 D-28 이 그 시험지의 지면에
   **배점을 아예 안 찍기로**("맞은 개수/전체") 정해 놨기 때문이다 — 배점을 안 보여주는
   시험지의 만점을 어떻게 잡을지는 제품 결정이라 임의로 바꾸지 않았다. **원장님 판단 필요.**
3. **판단 불가를 화면에 어떻게 보여줄지.** 실측 2%가 `합계_100_불가` 다. "문항을 더 넣어
   달라"는 안내가 맞는지, 그 학교 눈금 밖 값을 허용할지는 제품 결정이다.
   지금은 **지어내지 않는 쪽**으로 고정했다.
4. **공유 DB 쓰기 게이트.** `persistPredictedPaper` 는 앱 런타임 경로(원장 본인의 시험지 생성)라
   `--apply` + `ALLOW_SHARED_IMPORT=1` 게이트를 걸지 않았다. 그 게이트는 문제은행 대량 적재용
   이라고 읽었다. 스크립트 진입점은 만들지 않았다. **다르게 봐야 하면 알려 달라.**
5. 공용 파일 3개 수정(§1 표의 ⚠️) — 다른 세션과 겹치면 병합 시 확인 필요.
6. **API 계약을 `test.contract.ts` 가 아니라 `scoreNormalizer.contract.ts` 에 뒀다.**
   병렬 세션이 공용 계약 파일을 동시에 고치면 병합이 충돌해서다. 합치는 편이 낫다고 보면
   옮기면 된다 — 스키마 이름은 그대로 쓸 수 있다.
7. **`POST /api/tests/predicted` 는 근거 목록을 클라이언트에서 받지 않는다.** 대상 시점만 받고
   컷오프는 서버가 적용한다(누출 차단). 화면이 "이 회차들로 예측해 줘"를 고르게 하려면
   설계를 다시 봐야 한다 — 지금은 **고를 수 없게** 막아 둔 것이 의도다.

## 6. 적재 경로 — 무엇을 만들었나 (2차 지시)

### `persistPredictedPaper(input)`

`composePredictedPaper` 결과를 `Test` 1행 + `TestProblem` n행으로 한 트랜잭션에 저장한다.
**조정 배점은 `TestProblem.score` 에만 쓴다.** `problem` 테이블에는 `update` 를 아예 부르지 않는다.

저장 직전에 **만점을 다시 센다.** 보정기가 이미 100 을 보장하지만, D-45(만점 100 아닌 시험지는
출제·채점에서 제외)를 우회하는 유일한 길이 "손으로 만든 배점 배열을 그대로 저장하는 것"이라
한 번 더 막는다. 합이 어긋나면 **한 행도 쓰지 않고** 거부한다.

거부 사유: `판단_불가` · `만점_불일치` · `권한_없음` · `대상_없음` · `문항_불일치`.

멱등이 아니다 — `Test` 에 외부 고유 키가 없어 멱등 키를 만들 수 없다. 문서화했다.

### `saveManualScores(input)` — 11 §10.4

원장이 화면에서 고친 배점을 저장한다. **합계가 100 이 아니면 아무것도 쓰지 않고 거부하며**,
`합계 98.5 — 1.5점 남음` 을 그대로 화면에 띄울 수 있게 돌려준다.
자동으로 다른 문항을 건드리지 않는다. 테스트가 "거부 후 기존 배점이 그대로인지"까지 확인한다.

### 채점이 그 값을 읽게 했다 — 이게 없으면 적재가 헛돈다

`gradeAnswers` 의 배점 결정 순서를 이렇게 바꿨다:

```
1. TestProblem.score   ← 배점 보정기가 이 시험지에 매긴 조정 배점 (신규)
2. Problem.score       ← 원본 기출 배점
3. 균등 배분
```

1번이 NULL 이면 기존 동작과 **완전히 같다**(회귀 테스트로 고정).
`submitTestResult` 가 `tp.score` 를 넘기도록 한 줄 더했다.

**한 바퀴가 실제로 도는지 테스트로 고정했다** — 기출 2문항(10점) + 자작 3문항(NULL)을 섞은
시험지에서:

```
보정 전 만점  80  (10 + 10 + 20×3)   ← 11 §10.1 그 버그
보정 후 만점 100                      ← 적재된 TestProblem.score 를 채점이 읽는다
```

## 7. API Route (3차 지시)

### `POST /api/tests/predicted` — 예측 문제지 생성 + 적재

요청은 **무엇을 예측할지**만 받는다. 근거로 쓸 과거 회차 목록은 받지 않는다 — 클라이언트가
고르게 하면 누출 차단이 무너지기 때문이다(11 §3 L5).

```
{ classId, studentId?, testDate, rangeStartUnitId?, rangeEndUnitId,
  unitIds: [...],                       // 문제은행에서 재료를 뽑을 단원
  series: { school, level, grade, subject },
  target: { year, semester, round } }   // 이 시점 "이전" 자료만 근거가 된다
```

파이프라인은 `src/lib/predictor/generatePredictedPaper.ts` 한 곳에 모았다(Route 는 세션·검증·
상태코드만 본다 — `generateDraftTest` 와 같은 구조).

```
반 소유권 → 그 학교 과거 회차 + 코호트 적재(대상 시점 이전만)
         → 만점 100 신뢰 가드(11 §11) → 청사진 예측 → 문제은행 후보 조회
         → 조립 + 배점 보정(합계 100) → TestProblem.score 적재
```

상태코드: `201` 생성 · `400` 형식 오류 · `401` 미인증 · `403` 남의 반 ·
`404` 반 없음 · `422` **판단 불가**(근거 없음 / 눈금 없음 / 후보 없음 / 합계 100 불가).

응답에 `evidenceCount` 와 `confidence` 를 같이 실어 보낸다 — 근거가 1회차뿐이면 confidence 가
0.27 로 낮게 나오고, 화면이 그걸 그대로 경고로 쓸 수 있다. **근거가 0이면 시험지를 만들지 않고
422 로 거절한다** — "0문항 0점짜리 시험이 예상됩니다" 를 다시 내지 않기 위해서다.

### `PATCH /api/tests/{id}/scores` — 원장 수동 배점 조정

```
{ scores: [{ orderIndex, score }, ...] }
```

합계가 100 이 아니면 **422 + `합계 98.5 — 1.5점 남음`** 이 그대로 응답에 실린다. 화면은 이
문구만 띄우면 된다. 거부되면 기존 배점은 **한 행도 안 바뀐다**(테스트로 고정).
상태코드: `200` · `400` 형식/문항 수 불일치 · `401` · `403` 남의 시험지 · `404` · `422` 합계 불일치.

### 검증

10개 API 테스트를 RED(모듈 없음) 확인 후 구현했다. 그중 **누출 차단**이 핵심이다 —
미래 회차만 심어 두고 요청하면 근거가 0이 되어 422 가 나와야 한다. 이 테스트가 실제로 무는지
컷오프 필터를 지워서 확인했다(`1 failed`, 원복 후 초록).

실제로 나온 시험지 한 장(테스트에서 찍어 본 값):

```
문항 10 · 만점 100 · 눈금 [8, 10, 12]
배점 [8,8,8,8,10,10,12,12,12,12]
유형 객관식 8 + 서술형 2
못 채운 칸 0 · 근거 회차 1 · confidence 0.27
```
